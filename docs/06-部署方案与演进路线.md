## 1. 环境矩阵

| 环境 | 形态 | 用途 |
|---|---|---|
| dev | 单机 Docker Compose（全组件最小拓扑） | 日常开发、联调 |
| benchmark | K8s 集群 + 独立压力源节点 | 由 benchmark-small / benchmark-large 分档执行（§05） |
| benchmark-small | 10~15 台 8C16G 虚机 | 10 万 tick/s、10 万连接、100 万规则和核心故障恢复 |
| benchmark-large | 最低 8 个专用 8C16G WS 节点 + 2 个 8C16G 压力源节点，数据平面独立部署 | 百万 WS 连接、分级推送和重连风暴，不与 small 共用资源口径 |
| demo | K8s 集群（缩配） | 演示部署 |

## 2. docker-compose 开发拓扑（实际，2026-09 校准）

```yaml
services:
  mysql:            image: mysql:8.0                  # 23001；initdb 挂载 migrations（首启建库）
  redis:            image: redis:7.4-alpine           # 23002
  kafka:            image: apache/kafka:4.1.0         # 23003；KRaft 单节点
  kafka-init:       执行 deploy/kafka-init.sh          # 7 个 Topic 显式创建（auto.create 关闭）
  clickhouse:       image: clickhouse/clickhouse-server:26.3   # 23004(HTTP)/23005(native)
  # ---- 以下按 profile 启用（默认不起）----
  apisix:           image: apache/apisix:3.13         # profiles: [edge]；23010/23011/23012
  flink-jobmanager / flink-taskmanager:
                    image: flink:1.20-java21          # profiles: [flink]；作业经 make flink-submit 提交
  prometheus / alertmanager / grafana:                # profiles: [obs]
  doris:            image: doris-all-in-one-2.1.7     # profiles: [doris]；U2 归档启用时切 3.x
```

要点：基础设施默认四件套（MySQL/Redis/Kafka/CK）+ Topic 初始化；**Go/Java/Python 服务不走
compose**（宿主机进程 `make run-*` 或 IDE，见注记①）；Doris 按 U0/U1 口径默认关闭。

## 2.1 用户规模启动与扩容流程

U0~U5 阶段阈值与升级触发条件以 [07-设计基线与验收口径](./07-设计基线与验收口径.md) §4 为权威（本文不重复罗列）。

每次升级前必须完成一次容量检查：峰值在线连接、tick 速率、告警速率、Kafka lag、Redis 内存、WS 出口带宽和恢复时间。用户数未达到下一档但任一容量指标先达到阈值时，按容量指标提前升级；用户数达到下一档但容量指标未达到时，只扩充业务副本，不自动扩充整套基础设施。

U0~U1 允许核心组件单副本和混部，适合启动、开发和内测；U2 引入基础主从和滚动发布；U3 使用 benchmark-small 的实时/推送/查询隔离；U4~U5 使用 benchmark-large 的连接层专项资源。所有阶段沿用同一 Topic、Protobuf、REST/WS 协议和告警投递语义。

## 3. K8s 生产拓扑

### 3.1 namespace 与资源隔离（见架构文档 §8）

ns-realtime / ns-push / ns-query / ns-ai / ns-offline，配合 ResourceQuota + PriorityClass（realtime 最高）。

### 3.2 有状态组件部署

| 组件 | 方式 | 关键参数 |
|---|---|---|
| Kafka | Strimzi Operator | RF=3, min.insync.replicas=2, 3 broker |
| Flink | Flink Kubernetes Operator | HA mode, checkpoint 30s 增量, RocksDB |
| ClickHouse | Altinity Operator | 2 shard × 2 replica |
| Doris | Doris Operator | 3 FE + 3 BE |
| MySQL | 云托管或 mysql-operator | 半同步主从 + Orchestrator |
| Redis Cluster | Redis Operator | 3 主 3 从 |

### 3.3 无状态服务部署要点

```yaml
# 所有业务服务/推送服务通用模板要点
replicas: >= 2
strategy: RollingUpdate (maxUnavailable: 0)     # 滚动不中断
topologySpreadConstraints: [zone]               # 反亲和
readinessProbe / livenessProbe                  # /healthz /metrics
resources: requests == limits (ns-realtime)     # Guaranteed QoS
podDisruptionBudget: minAvailable: 1
autoscaling (HPA): CPU 70% / 自定义QPS指标, min 2 max N
```

ws-gateway 缩容流程：**SIGTERM 触发 hub.DrainAll 下发 `sys.drain` 帧**（preStop 钩子仅宽限等待，实现口径见 deploy/k8s/README）→ 客户端重连其他实例 → terminationGracePeriodSeconds 60s。

## 5. 演进路线

> ⚠️ 本节 M2=高并发压测 / M3=智能化 / M4=扩展验证 为 V2.1 规划态编号，**已废弃**（注记⑦）；
> 里程碑权威定义（M1 核心闭环→M2 可靠性与可观测→M3 K8s 化与小规模 HA→M4 压测/混沌/容量调优→M5 AI/补数/多市场）与
> 分支执行排期以 docs/09 §5.1 为准，本节保留为历史规划明细。

### M1 核心链路闭环（4~6 周）

- compose 全链路跑通：模拟源→Kafka→Flink（价格/涨跌幅规则）→alert_event→notify（inbox 落库+推送）→ws-gateway→PC/H5 收到推送并 ACK
- 双端：登录、自选、实时行情、K线、规则 CRUD、告警中心（含 cursor 补拉）
- 全链路延迟打点可见（Grafana 面板 v1）

**验收**：功能演示 + 各段延迟直方图。

### M2 高并发与压测（4~6 周）

- K8s 化（ns 隔离、HPA、PDB、探针）
- Kafka 24 分区调优、Flink 反压调优、CK 批量写调优
- 压测平台内建（seeder/simulator/调压控制台）
- 指标条件规则（RSI/MACD）、防抖冷却、离线补拉

**验收**：small 完成 S1~S4、S6 的 10 万连接基线和 100 万规则验证；百万连接在 benchmark-large 单独完成，不把两套资源结果混合。

### M3 智能化（3~4 周）

- ai-query（NL2Condition + 条件缓存 + 熔断）
- 条件自动分组（离线批算）
- 公式沙箱（M3 末，视进度裁剪）
- 邮件适配器（可选）

### M4 扩展性验证（3~4 周）

- 模拟 HK/US 市场源接入（验证 market 元数据驱动，上层零改动）
- S5 扩展性实验 + 全量实验复测出论文数据
- 冷数据 S3 归档策略验证

**验收**：NFR-10 线性度报告 + 全部实验数据归档。

## 6. 可观测体系

| 层 | 内容 |
|---|---|
| 指标 | Prometheus：链路延迟分解、Kafka lag、Flink 反压/checkpoint、CK 写入、ws 连接数/推送成功率、缓存命中率、限流计数 |
| 面板 | Grafana：总览 / realtime / push / query / bench 五套 |
| 日志 | Loki：结构化 JSON（traceId 贯穿 gateway→kafka header→flink→notify） |
| 追踪 | OpenTelemetry Collector + Tempo（HTTP + Kafka + WS 追踪）；SkyWalking 仅作为替代方案 |
| 剖析 | Go pprof + Pyroscope：CPU、内存、阻塞和锁火焰图 |
| 告警 | Alertmanager：断流、lag 水位、checkpoint 失败、推送成功率 < 99%、死信增长 |
| 混沌 | Chaos Mesh CR 编排 §05-S6 全部场景，实验记录自动化归档 |

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| Flink checkpoint 大状态恢复慢 | 增量 checkpoint + 规则状态精简（只存生效规则）+ 对账兜底 |
| WS 重连风暴（网关批量重启） | 客户端抖动退避 + LB 慢启动 + 网关 readiness 门控；告警通过 alert-inbox/cursor 补拉 |
| CK 写入放大（小批量高频） | ingest 攒批（每 5k 行或 1s）+ 异步；写失败不提交 offset 自动重放（U0 无独立死信 Topic） |
| 压测源与被测系统抢资源 | 模拟源独立 ns-offline 节点，Pod 反亲和 |
| AKShare 接口变动 | 补数任务多数据源降级（Tushare 备份），失败不阻塞主链路 |
