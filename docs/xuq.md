股票预警一般是怎么做？股票预警怎么做

股票预警核心：设置**价格、涨跌幅、指标、时间**条件，达到阈值软件自动提醒（弹窗、推送、短信），分为软件自带预警、自编条件预警、第三方工具三类。

> 提示：预警仅做提醒，**不构成投资建议**，不会保证买卖收益。

## 一、普通券商 APP 自带预警（最常用）

绝大多数炒股软件（东方财富、同花顺、券商自家 APP）都有，操作逻辑大体一致：

1. 打开个股页面，找到【预警 / 提醒】按钮
2. 选择预警类型：

- **价格预警**：高于 X 元、低于 X 元（最常用，比如破位、压力位、支撑位）
- **涨跌幅预警**：涨幅＞5%、跌幅＞‑4%
- **涨跌额预警**：上涨超过 0.8 元
- **时间预警**：开盘、收盘、某一时间点提醒

1. 设置阈值，开启消息推送，触发后手机推送通知。

局限：只能做简单价格、涨跌幅，**不能做复杂技术指标预警**（MACD 金叉、RSI 超买超卖等）。

## 二、PC 端专业软件条件预警（通达信、同花顺 PC）

支持技术指标预警，可以监控 MACD、KDJ、均线突破、成交量等信号。

### 通达信预警流程

1. 顶部菜单：【功能】→【预警系统】→【条件预警设置】
2. 添加监控股票池（把要盯的票加入）
3. 添加预警条件：
   - 系统自带：上破 / 下破价格、涨跌幅、成交量放大
   - 自定义：导入公式，例如 MACD 金叉、5 日均线上穿 10 日均线
4. 开启【条件预警开关】，电脑要保持软件运行，关机就失效。

> 重点：通达信本地预警，**电脑必须开机运行软件**，关闭软件不会收到提醒。

## 三、指标类云端预警（手机也能收指标信号）

同花顺、东方财富部分云端预警，把公式上传云端运算，手机不用挂软件也能推送。

1. 编写 / 选用技术公式
2. 在软件预警中心，设置云端条件：如 KDJ 低位金叉、放量突破 20 日线
3. 添加监控股票，开启推送。

> 部分高级云端预警是付费功能。

## 四、常见预警条件参考（仅供思路，非买卖建议）

1. 价格类：股价跌破 20 日线、突破前期高点
2. 涨跌幅类：单日跌幅＞‑7%，涨幅＞6%
3. 成交量：成交量大于 5 日均量 2 倍（放量）
4. 指标类：MACD 金叉死叉、RSI＞80 超买、RSI＜20 超卖

## 五、重要坑点

1. **本地预警（通达信 PC）**：电脑关机、软件关闭，预警完全失效。

2. **云端预警延迟**：行情剧烈的时候，会有几秒～几十秒延迟。..

# 股票预警的数据来源

预警本质就是软件**持续读取行情数据**，和你看 K 线、分时是同一套数据源，条件满足就触发提醒。信息仅供参考，不构成投资建议。

## 1、原始源头：交易所

上交所、深交所产生原始行情：

- 成交价格、成交量、盘口、分时、K 线、涨跌幅，每一笔撮合数据。
- 交易所只把行情授权给**行情服务商**，普通用户不能直连交易所拿数据。

## 2、行情服务商（中间分发层）

国内主要：通达信、同花顺、东方财富、恒生、聚源、万得等。

- 向交易所购买行情授权，接收交易所数据流。
- 做清洗、加工：合成 1 分钟 / 5 分钟 / 日 K，计算 MACD、KDJ、均线等衍生指标。
- 再把处理好的数据卖给券商、各类软件。

> 
> 分两类行情：

1. **Level‑1 普通行情**：免费，绝大多数 APP 预警用这个，秒级刷新，日常够用。
2. **Level‑2 十档盘口逐笔**：付费，部分高级预警会基于 Level2 数据。

## 3、你用的软件怎么拿到数据

### ①券商 APP

券商向行情服务商采购行情数据 → APP 拿到数据 → 在手机本地做预警判断。

> 
> 手机端简单预警（价格、涨跌幅）：**数据传到你手机，手机本地对比阈值**；手机没网、后台被系统杀掉，预警会漏。

### ②通达信 PC 本地预警

软件接收服务商推送行情流，**在你自己电脑内存里实时计算条件（均线、MACD 金叉）**。

> 
> ⚠️关键点：数据是流到你的电脑，电脑 CPU 运行公式判断；电脑关机、软件关闭，数据断流，预警失效，不是云端跑的。

### ③云端预警（同花顺 / 东财云端条件预警）

你的条件公式提交到服务商服务器；**服务器持续接收行情，在云端批量运算全部监控股票**。触发后推送到你手机。

> 
> 手机不需要挂软件，服务器 24 小时跑，高级功能大多收费。

## 4、预警里的指标数据怎么来

MACD、KDJ、RSI 这些**不是交易所给的**。
交易所只输出：开盘、最高、最低、收盘、成交量。
软件拿到基础 K 线数据后，按公式实时计算出指标数值，再拿这个数值和你的预警条件对比。

## 5、会有延迟、漏预警的原因

1. 行情链路延迟：交易所→服务商→软件，网络链路会有几十～几百毫秒延迟；行情剧烈波动时还会拥塞。
2. 本地预警：手机后台被杀、电脑休眠断网，数据停止接收，不会提醒。
3. 云端预警：服务器负载高，极端行情也可能出现推送慢。

## 简单总结数据流链路

交易所原始行情 → 行情服务商加工 → 给到软件（本地 / 云端） → 和你设置的预警条件对比 → 触发推送提醒。

# 行情订阅+预警SaaS完整架构思路
> 仅技术架构讨论，不构成投资建议。
你的业务：对接上游行情服务商订阅实时Tick/K线；内部做规则引擎（价格、指标、金叉等）；对内给公众号粉丝推送；对外做付费SaaS：提供API/SDK，客户提交预警规则，触发后推送给客户。

## 一、数据流总览
上游行情服务商（WebSocket订阅） → 行情接收网关 → Kafka（消息队列，削峰、解耦） → 流计算引擎做规则判断 → 触发告警事件Kafka → 通知分发服务 → 多渠道输出（公众号、webhook回调、短信、邮件、推送）
历史行情存入OLAP，用于回测、查询历史K线/指标。

## 二、存储&计算选型：Flink + CK / Doris，要不要流式数据库
### 1、Flink定位
Flink做**状态流计算**：维护K线状态、计算MACD/KDJ、维护海量用户预警规则、价格阈值判断、窗口计算、去抖动（价格在阈值来回跳避免风暴告警）、状态持久化。
> 不建议把预警规则全部放Redis轮询扫表，用户量大之后性能很差，Flink CEP/KeyedState才是标准方案。

### 2、ClickHouse vs Doris
两者都是OLAP，**不是用来做实时预警判断，是存历史行情、历史告警记录、回测数据**。
- **ClickHouse**：写入吞吐极高，单表时序查询强；Join弱，更新差。适合纯行情原始tick、K线存储，只追加不修改。缺点并发不高，不适合大量业务查询。
- **Apache Doris**：Join好、支持Upsert、MySQL协议、并发更高。如果你除了行情，还要频繁关联用户、订阅规则、租户信息，选Doris更舒服，运维成本更低。

> 不建议：Flink+CK/Doris直接用来做实时预警触发。预警判断在Flink内存状态，OLAP只做存储与后台查询。

### 3、流式数据库要不要上（RisingWave/Materialize）
流式数据库 = 流计算+存储一体，不用维护Flink集群。
- 小规模、团队缺Flink运维人力：可以选RisingWave，SQL写指标计算，物化视图持续更新，直接拿结果做判断，简化架构。
- 大规模SaaS、复杂自定义预警公式、多租户隔离：优先Flink，可控性更强。

### 4、必须补充的其他存储
1. **Redis Cluster**：
    - 缓存最新标的快照（最新价、指标值）
    - 用户订阅元数据、租户配置、限流配额、冷却防风暴配置
2. **MySQL/PostgreSQL**：业务库：用户、付费订单、SDK‑key、回调地址、告警模板、渠道配置。
3. **Kafka**：核心中间件，全链路解耦：原始行情topic、计算后指标topic、告警事件topic、通知重试topic。

> 不要把业务元数据放CK/Doris。OLAP适合分析，不适合高频业务CRUD。

## 三、网关分两类：行情接入网关、对外服务网关
### A、行情接入网关（对接上游行情服务商）
上游服务商一般提供WebSocket行情流。
- 技术：Netty / Go写轻量WebSocket客户端集群，做连接池管理，多数据源容灾切换，协议解析、数据标准化（统一字段、时间戳），输出到Kafka。
- 不建议Flink直接连外部行情websocket，外部网络抖动会搞崩Flink任务；网关层做重试、断线重连、故障隔离。

### B、对外业务网关（给你的付费客户用）
客户提交预警规则、调用API、使用SDK。
技术选型：
1. API网关：**Kong / APISIX**，做鉴权（API‑Key）、限流、租户配额、HTTPS、路由、日志、计费统计。
2. 协议：
    - REST API：客户提交/增删预警规则，查询告警历史。
    - WebSocket：可选，客户长连接直接接收告警推送。
3. SDK：封装REST+WebSocket，多语言（Python/Java/Go），本质就是封装你的开放API。

> 客户提交规则流程示例：
`客户SDK → APISIX网关鉴权 → 业务API服务 → MySQL存规则元数据 → 推送规则到Flink（通过Kafka广播topic）→ Flink加载新规则进入状态，开始监控该标的`

## 四、告警触发之后，对外推送的市场主流方案
客户付费接入，你触发告警，怎么给到对方。**现实中一般组合使用，不是单一种**。

1. **Webhook回调（SaaS客户最常用）**
客户提交规则时带上自己回调URL；告警事件出来，通知服务POST http payload到对方url。
- 优点：客户不需要维持长连接，简单集成。
- 必须做：超时控制、重试队列（Kafka）、指数退避、失败死信、签名校验防篡改、防雪崩。
> 绝大多数量化SaaS、告警平台对外都是Webhook优先。

2. **WebSocket长连接推送**
客户建立wss连接，鉴权，订阅自己告警事件；服务端主动push JSON告警消息。
- 适合低延迟、大量告警的客户；缺点客户端必须保持在线，要处理心跳、断线重连。

3. **MQ方式（面向机构大客户）**
你部署Kafka/Pulsar，分配topic+账号给客户，告警写入客户topic，客户消费。
适合高吞吐机构；成本高，中小客户不会用。

4. **邮件 / 短信**
适合个人用户、公众号粉丝；不适合对接开发者客户。短信成本高，只能做重要告警，不能高频。

5. **Push（APP推送）**
如果你自己有APP；对外给第三方开发者一般不用。

> ✅ 生产SaaS标准组合：
- B端付费开发者：**Webhook为主，WebSocket可选高级版，MQ作为机构增值服务**
- C端公众号粉丝：公众号模板消息 + 邮件

### 推送层架构
Flink输出告警事件 → Kafka告警Topic → 通知消费worker集群。worker根据用户配置分发到不同渠道：webhook/公众号/短信/邮件；失败消息进重试topic，多次失败进死信队列做监控告警。

## 五、坑点（生产必须考虑）
1. **告警风暴**：价格在阈值来回抖动，短时间大量触发。Flink做状态冷却、防抖，同一规则N秒内只输出一次告警。
2. **规则下发一致性**：客户新增/修改预警规则，需要可靠广播到全部Flink算子。
3. **行情延迟**：上游行情拥塞，会连带预警延迟，要埋监控打点。
4. **Webhook客户侧慢/宕机**：一定要异步+重试，不能阻塞Flink流计算。
5. **多租户隔离**：Flink侧做好key隔离，计费、限流，防止一个付费客户把系统打满。
6. OLAP不是KV库，不要拿ClickHouse/Doris做实时状态查询。最新行情快照放Redis。

## 最简起步版本（中小团队）
上游行情WebSocket接入网关 → Kafka → Flink（规则计算告警）
存储：MySQL(业务) + Redis(快照缓存) + ClickHouse(历史tick/k线)
对外网关APISIX，客户提交规则REST API；告警主要走Webhook；C端粉丝走公众号推送。

# 行情数据：网关清洗入Kafka，还是原始丢Kafka由Flink清洗
## 两种主流方案对比
### 方案1：接入网关做解析、清洗、标准化 → 输出干净消息进Kafka（**生产主流推荐**）
链路：上游服务商WebSocket原始报文 → **行情接入网关（Go/Netty服务）**
1. 网关职责
- 网络层：维持上游长连接、断线重连、多数据源容灾、心跳保活、流量控制；隔离外部不稳定网络，不让外部抖动冲击Flink。
- 协议解析：把服务商自定义二进制/JSON报文，解析拆出字段。
- 基础清洗：丢弃脏包、时间戳补全、字段对齐、统一结构体、过滤无效tick、去重、错误报文打日志丢死信topic。
- 输出：标准化后的统一JSON/Protobuf消息写入Kafka原始行情Topic。

2. 优点
- Flink只消费已经规整好的数据，专注**业务逻辑：K线聚合、指标计算、预警规则匹配**，不耗算力在协议解析脏数据处理。
- 外部报文变更、协议升级，只改网关，不用发布Flink任务；Flink任务尽量少发布，流任务重启成本高。
- 脏数据、异常报文在网关层拦截，不会污染Flink流状态。

3. 缺点
需要维护一套网关服务。

---

### 方案2：原始报文直接丢Kafka，全部交给Flink做解析+清洗
链路：上游原始报文 → 直接投递Kafka → Flink消费原始报文，内部完成解析、清洗、标准化。

1. 适用场景
- 原型验证、快速demo，不想额外开发网关服务。
2. 严重弊端，生产尽量避免
- 上游网络抖动、乱包、脏报文直接打进Flink，极易导致Flink算子报错、任务失败重启，**Flink状态会发生回滚，预警业务会中断**。
- 第三方行情服务商协议改动，需要重启Flink任务；预警流任务重启期间，全部预警规则暂停工作。
- Flink不适合做外部长连接客户端，所以就算解析放Flink，**长连接接收依然要外部服务**，不可能Flink直连上游websocket。

> 重点：**Flink不要直接对接外部行情websocket源**。外部网络问题会直接搞崩Flink JobManager/TaskManager。接收长连接一定独立网关。

## 网关清洗到什么程度交给Kafka？
网关只做**通用基础清洗，不做业务计算**：
✅做：协议解析、字段统一、时间戳校正、去重、过滤无效数据、格式转为Protobuf/JSON。
❌不做：K线合成、MACD/KDJ计算、预警规则匹配，这些下沉给Flink。

Kafka里存**标准化原始Tick/分时**，Flink消费这个topic做窗口聚合、指标计算。

## 完整链路回顾（生产标准）
> 上游行情服务商WebSocket
→ 行情接入网关（长连接、协议解析、基础清洗标准化）
→ Kafka(tick_raw_topic)
→ Flink消费tick_raw_topic
  → 窗口计算生成1min/5min/日K
  → 计算技术指标MACD/KDJ
  → 匹配海量用户预警规则
  → 命中告警输出到kafka(alert_event_topic)
→ 通知分发服务消费alert_event_topic，分发webhook/公众号/短信等

## 补充边界情况
1. 如果上游行情服务商本身输出标准结构化JSON，脏包很少：网关可以做很薄，只做连接管理，简单校验就直接丢Kafka，清洗逻辑少量下沉Flink。
2. 脏数据一定不要丢弃无日志：网关解析失败的报文，写入单独 `dead_topic`，用于事后排查，不要直接扔掉。

## 配套小细节
- 序列化优先选 **Protobuf**，相比JSON，Kafka存储占用小，Flink解析更快。
- Topic分区数：根据tick吞吐设置，标的多、tick量大，分区要足够，Flink并行度和topic分区匹配。

# 多市场扩展架构：A股 → 港股/美股/虚拟币，设计要点
核心原则：**上层业务、规则引擎、告警、推送完全与市场解耦；仅行情接入层做各市场适配**。不要写A股专用硬编码逻辑，后续新增市场只新增一套行情接入，Flink、存储、推送几乎不用改。
> 技术架构讨论，虚拟币国内监管风险，仅讨论架构层面，不建议实际上线虚拟币相关对外服务。

## 一、核心设计：多市场元数据驱动（最重要）
所有标的带上统一元字段，不要靠字符串判断市场。
每条行情消息（Tick/K线 Protobuf）强制字段：
```
market: enum { A_SHARE, HK, US, CRYPTO } // 市场枚举，新增市场只加枚举
symbol: string // 标的代码，例如 600000, AAPL, 00700, BTC‑USDT
exchange: string //交易所
timestamp: int64
price, volume, amount ……
```
MySQL业务库：
- `market` 市场字典表，维护各个市场时区、交易时间、最小变动单位、是否支持复权、交易时段。
- `symbol_meta` 标的元数据表：`market+symbol` 作为联合唯一主键，存每个标的基础信息。
- 用户预警规则表：每条规则都携带 `market + symbol`。

> 新增一个市场，只需要：
1. 新增市场枚举、市场字典配置；
2. 新增一套【行情接入网关】对接对应数据源；
3. 把该市场tick写入同一个 `tick_raw_topic`（Kafka）；
4. 加载该市场标的元数据；
Flink、告警、推送、API网关**不需要修改代码**。

> ❌ 反模式：代码里面大量 `if symbol.startsWith("60")` 判断A股，扩展市场就到处改代码。

## 二、行情接入：每个市场独立接入网关实例
每个市场行情源不一样：A股一个服务商，港股另一个，美股、加密币又是不同API/WebSocket源。
- 部署多组行情网关：`gateway‑a`、`gateway‑hk`、`gateway‑us`。
- **所有网关输出格式完全统一的Protobuf，写入同一个Kafka `tick_raw_topic`**。
- 网关职责只处理各个源的差异：协议解析、时区转换、时间戳对齐、脏数据过滤，输出统一结构体。
- Kafka Topic不需要按市场拆分；如果吞吐巨大，可以按market做分区key，同一个market+symbol落到同一个分区。

> 好处：某一个市场行情源挂了，只影响该网关，不会搞垮整体系统；新增市场只新增网关服务，流计算任务不动。

## 三、Flink层怎么兼容多市场
Flink消费统一 `tick_raw_topic`，**全部逻辑基于 market+symbol 主键处理**。
1. K线窗口：不能写死A股交易时间。窗口参数从外部元数据（广播流）读取对应market的交易时区、开盘收盘时间。
> 不同市场时区、交易日历完全不一样，不能硬编码窗口。通过Flink广播流把 `symbol_meta`、市场交易时间下发到算子。
2. 指标计算(MACD/KDJ等)：计算公式是通用数学，和市场无关；只依赖OHLCV，所以不需要改。
3. 用户预警规则：Flink KeyedState 的 key = `market+symbol`；规则广播topic下发规则的时候带上market字段。
4. 告警输出：告警事件 `alert_event_topic` 消息同样带上 market 字段；推送层只透传，不关心是什么市场。

> 关键点：**Flink不要写死任何市场业务逻辑，全部配置化、元数据驱动**。

## 四、入库策略：是Flink直接入库？还是异步入库，推送与入库并行？
你提到入库用途：历史行情存储 + 用户AI Agent统计、告警事件统计。
### 两种数据：①行情原始数据 ②告警业务事件
1. **Tick/K线时序数据（ClickHouse/Doris）**
方案：**Flink Sink异步入库OLAP，和告警推送并行，不要串行**。
- 链路：Flink消费tick_raw_topic
  - 分支1：流计算，指标计算，匹配预警规则 → 输出告警事件到 `alert_event_topic`（告警链路，高优先级）
  - 分支2：把tick、聚合后的K线异步sink写入ClickHouse/Doris（历史存储链路）
> 两个分支并行；**入库失败不能阻塞告警业务**。入库是次优先级，告警触发是主业务。
- 风险：CK写入抖动，如果同步写会阻塞Flink算子。所以用异步sink；写入失败的数据落死信topic，后续补刷，不能影响预警。
> 不要做成：先入库成功，才做预警。入库是事后存储，预警是实时链路。

2. **告警事件、用户AI Agent统计数据**
AI Agent统计场景：用户告警触发统计、规则命中率、信号统计、回测数据。
- 实时告警事件 `alert_event_topic` 分两路消费：
  1. 通知分发服务：webhook/公众号等推送（实时业务）
  2. Flink/独立消费任务：消费alert_event_topic写入Doris/CK，用于统计、报表、AI Agent分析。
- 用户业务元数据（规则、付费配置）依然放MySQL。

### 要不要异步入库（独立消费Kafka做入库，不从Flink sink入库）
两种选型：
1. **Flink异步Sink写入CK/Doris**（简单，中小规模）
Flink内做K线聚合，算完一方面输出告警，一方面sink时序库。适合起步。
2. **完全解耦：独立消费服务消费tick_raw_topic、alert_event_topic入库**（大规模生产）
Flink只负责实时计算与告警输出；入库交给独立消费程序。
优势：OLAP库故障、慢写入完全不碰Flink集群；入库任务挂掉不影响预警；可随时重启重放Kafka历史数据补数据。
> 建议：后期多市场数据量大，走向方案2，独立消费任务做入库。

## 五、存储层适配多市场
1. ClickHouse/Doris时序表：联合主键 `market, symbol, timestamp`。所有市场tick、K线全部存在一套表，靠market字段区分。不要A股一张表、港股一张表。
2. Redis：缓存最新价格、最新指标，key设计 `{market}:{symbol}`，例如 `A_SHARE:600000`，`US:AAPL`。
3. MySQL业务表：所有规则、订阅全部带market字段。

# 未命中、历史K线、实时K线：查询链路设计
> 场景拆分：
1. **预警未命中**：这条tick/K线经过Flink，但不满足任何用户预警规则，不会产生alert_event。
2. 用户后续查询：实时K线、历史K线；有两种数据源选择：**自己库(CK/Doris)** vs **第三方行情API**。

核心结论：
- ✅ **历史K线：优先走自己的OLAP库（CK/Doris）**，前提是你已经持续入库；
- ✅ **最新实时K线/最新价格：优先Redis缓存**；
- ✅ **缺失的历史片段（启动晚、丢数据）：兜底调用第三方接口补数回写到自己库**；
- ❌ 线上业务查询不要每次直接透传调用第三方；第三方做兜底补数，不要做主查询源；
- ❌ **预警未命中的数据也要入库OLAP，只是不会生成告警事件**；预警命中/未命中是流计算业务分支，原始tick/K线都要落库，用于回测、AI Agent、用户查询。

## 1、预警未命中的数据怎么处理
Flink收到tick → 生成K线、计算指标
1. 匹配用户预警规则：
   - 命中 → 输出 `alert_event_topic`（告警事件）
   - **未命中：不输出告警事件，但tick、K线照常往下走到入库链路**
> 未命中≠丢弃数据。告警只是业务分支；原始行情时序数据独立落库CK/Doris。
> 用户以后做回测、看历史指标、AI Agent统计，需要全部历史，不能只有命中告警那部分数据。

> 两种入库模式回顾：
1. 中小规模：Flink异步Sink把tick、聚合K线写入CK/Doris。命中/未命中全部写入。
2. 大规模解耦：`tick_raw_topic` 单独一套消费任务做入库，**和Flink预警计算完全独立**。Flink就算挂了，只要Kafka还有数据，历史行情入库不受影响。推荐后期走这套。

## 2、用户查询：实时K线 / 当前价格
不要查CK/Doris拿最新实时价格，OLAP不适合高频点查。
链路：
> 用户API请求最新价格/当前K线 → API网关 → 查询 **Redis**
Redis key：`{market}:{symbol}`
存：最新tick、当前K线(1min/5min)、最新指标值。
> Redis数据来源：Flink计算完成后写入Redis，或者行情网关更新Redis快照。

Redis miss兜底：可以临时调用第三方行情接口返回，**同时回写Redis缓存**，下次命中缓存。不要每一次都打第三方。

## 3、用户查询：历史K线（比如查某只股票过去30天日线）
优先查自己的 Doris / ClickHouse。
- 条件：`market + symbol + time range`
- 返回OHLCV，给前端、SDK、AI‑Agent做回测、图表渲染。

### 会出现自己库查不到数据的情况
原因：
- 系统刚启动，之前历史数据没有；
- 服务宕机一段时间，中间一段tick丢失；
- Kafka保留时间有限，无法重放更早数据。

**兜底策略：分层**
1. 优先查本地OLAP；
2. 如果时间范围部分缺失，检测缺失时间片段；
3. 后台异步调用第三方历史K线接口，拉取缺失片段，写入CK/Doris；
4. 再从自己库返回给用户。
> 用户感知是正常返回，后台补数据。避免每次直接代理第三方API，第三方有限流、计费、延迟、可用性风险。

> 禁止模式：用户过来查历史，直接http代理透传给第三方接口返回。一旦第三方挂、限流、涨价，你的业务直接瘫痪。第三方是**数据源，不是你的查询服务**。

## 4、哪些数据才去调用第三方接口
第三方行情接口定位是：**初始化补数、故障补数、冷启动，而不是在线查询主路径**。
1. 系统上线初始化：批量拉取全市场历史K线灌入CK/Doris；
2. 检测到本地时序库时间片段空洞，后台补数；
3. 新增标的，预先拉取历史；
4. 本地发生大规模数据丢失故障做修复。

正常用户在线查询路径：`API服务 → Redis(实时) / Doris‑CK(历史)`。

## 5、告警事件查询（命中的告警记录）
告警事件在两个地方：
1. MySQL：存简要告警记录给普通用户分页查询（少量字段）
2. Doris/CK：完整告警事件，用于AI Agent、统计分析、大时间范围查询。

> 未命中不会产生告警事件，所以告警表里没有记录；但是原始tick/K线时序表里依然存在，用户回测可以看到当时价格指标，只是没有触发预警。

## 一、同花顺/通达信底层是怎么做的

2. **内部链路**

3. 防抖：阈值附近来回跳动，做冷却窗口，避免告警风暴。

1. 行情接入内网化，原始行情集群不暴露公网；对外只输出清洗后的标准化数据。

4. 内部补数、离线任务不能暴露公网；所有外部第三方行情源访问做代理，不直接暴露业务服务。
5. 防DDOS、接口签名；Webhook对外推送增加签名校验，防止被恶意调用。

- 写：实时tick/k线写入Kafka，再落OLAP；

核心选型思路：**语言不统一，按场景选最合适的，不强求一门语言贯穿全部；高吞吐低延迟服务优先Go；重业务复杂逻辑、流计算用Java；AI、数据脚本用Python；业务API/网关配套Node/TS；前端React**。
同时列出每个组件的痛点、为什么这么选、备选方案、不选的理由。

## 各模块详细说明、痛点、避坑

### 1. 行情接入网关 Go
> 职责：对接上游行情服务商WebSocket，多源容灾、心跳保活、协议解析、基础清洗、标准化protobuf，输出tick_raw_topic。
- 为什么Go：海量WebSocket长连接，协程开销极低；网络IO是主力，业务逻辑极少。
- **严格约束：网关只做网络和协议转换，禁止K线计算、指标计算、业务规则判断**。
- 痛点：Go写复杂表达式、业务逻辑笨重；所以不把业务放网关。
- ❌不选Python：GIL，大量长连接性能不行。
- ❌不选Flink直接连接外部websocket：外部网络抖动直接搞崩整个Flink任务。

### 2. Flink（Java）实时流计算层
> 职责：tick消费、K线窗口聚合，指标计算（TA‑Lib绑定Java），用户预警规则匹配，告警防抖，输出alert_event_topic。
1. 状态后端RocksDB，海量用户预警规则存在KeyedState。
2. 用户新增/修改预警规则，通过Kafka广播topic下发到Flink算子，**尽量避免重启Flink任务更新业务规则**。
3. TA‑Lib做标准指标；自定义公式解析可以把解析器编译到Flink；**不要在Flink内部做AI选股批量查询**。
4. 痛点：Flink任务重启代价高；尽量把可变业务配置通过广播流下发，减少发布。
5. 备选RisingWave：团队不想维护Flink集群时选；用SQL写指标，可控性下降，复杂自定义公式支持弱。

### 3. 业务微服务 SpringBoot Java
> 用户管理、付费、预警规则CRUD、公式管理、标的分组、权限、开放API业务逻辑。
- 大量事务、数据库操作、复杂业务逻辑，Java生态成熟。
- 当用户保存预警规则，业务服务把规则写入MySQL，同时发送消息到Kafka的rule_broadcast_topic，通知Flink加载规则。
- 重IO任务（推送、大量行情查询）剥离给Go服务，不要压SpringBoot。

### 4. Notify‑service 推送分发 Go
消费alert_event_topic，做分发：公众号、邮件、webhook回调、websocket推送。
- Webhook会大量向外发HTTP请求，Go http客户端并发性能优秀。
- 实现：超时控制、指数退避重试、失败进入死信topic。
- 痛点：不要在这里做业务计算，只做消息分发。

### 5. AI‑query‑service Python FastAPI（聊天选股NL2Condition）
> 用户自然语言转结构化查询条件，调用大模型；校验条件，组装Doris查询参数，包装回答。
- 大模型SDK、数据处理Python生态最好。
- 重要隔离：**AI服务只生成查询条件，真正筛选数据交给Doris执行**，杜绝大模型幻觉直接输出股票列表。
- 痛点：Python高并发弱；前面放APISIX限流，多实例水平扩容。
- 禁止把实时预警逻辑跑在Python。

### 6. 补数后台 Python Celery
负责系统冷启动、Doris空洞检测，调用akshare/yfinance/openbb拉历史K线，批量写入Doris。
- 全部是后台离线任务，有队列限速，**绝对不处理用户在线请求**。
- 不对外暴露HTTP接口，内部服务调用。

### 7. 存储层
1. **MySQL8.0：业务元数据**
用户、付费、预警规则、公式、分组。不存tick/k线时序。
2. **Apache Doris：主力OLAP**
tick、K线、历史告警事件，AI选股批量筛选。
> 为什么Doris而不是CK：你的平台有大量业务查询、多条件筛选、join用户/标的元数据；CK写入强，join弱，并发查询差。
> 如果后续tick吞吐爆炸，可以部分热tick用CK，Doris做查询。
3. Redis‑Cluster：热快照缓存，`market:symbol` 存最新价格、指标；限流、冷却。

### 8. APISIX 网关（统一公网入口）
所有前端、公众号、开放SDK全部经过APISIX。
能力：JWT登录鉴权、API‑Key付费客户鉴权、QPS限流、租户配额、请求签名、计费埋点、HTTPS。
> 内网服务（行情网关、Flink、Kafka、Doris）不暴露公网。

### 9. 公众号对接 Node‑TS
微信回调是短连接，Node处理回调非常合适；完成openid绑定、接收用户指令，调用Java业务服务，接收notify‑service推送消息。

### 10. 前端 React+TS+Antd Pro
后台管理页面：行情看板，预警配置，公式编辑器，AI聊天对话界面，标的分组管理。

## 完整数据流串一遍
1. 各市场行情源 → Go行情接入网关（解析清洗） → Kafka tick_raw_topic
2. Flink(Java)消费tick_raw_topic：K线聚合、指标计算、匹配预警规则；命中输出alert_event_topic；tick/k线写入Doris；最新行情更新Redis。
3. 用户保存预警规则：SpringBoot业务服务写入MySQL，同时发送规则到Kafka广播topic，Flink动态加载规则。
4. alert_event_topic被Go的notify‑service消费：分发公众号、webhook、邮件；失败消息进入重试队列。
5. 用户AI聊天选股：前端请求 → APISIX → Python FastAPI AI服务，大模型把自然语言转为查询条件，下发Doris执行筛选，结果再交给大模型润色返回。
6. 历史行情查询：history‑query‑service优先查Doris，缺失片段丢给Python Celery补数任务后台补数据。

## 开发部署落地策略（因材施教，因地制宜）
### 起步阶段（小规模原型）
- Kafka单节点；Doris极简部署；Redis单主；MySQL单机。
- Go网关、SpringBoot、Go推送服务、Python AI服务全部容器化Docker Compose跑。
- Flink先做session集群。
- 补数任务Celery单机。

### 生产阶段
- Kafka集群、Redis‑Cluster、Doris集群；MySQL主从读写分离。
- 全部微服务上K8s，水平扩缩容。
- Flink on K8s，RocksDB状态后端。
- APISIX集群做公网网关。

## 关键避坑清单
1. **不要一门语言通吃全部**：不要强行全部Java，也不要全部Go；网络IO选Go；流计算选Java；AI数据脚本选Python，各尽其职。
2. **实时链路和离线/AI链路严格隔离**：Flink预警链路最高优先级；AI筛选、补数任务故障，不能影响预警。
3. Python只做AI、离线补数，**不要承担实时流、高并发推送**。
4. 内网服务(Kafka、Doris、行情网关)严禁暴露公网；公网只暴露APISIX网关。
5. 用户自定义公式执行必须沙箱，防止表达式注入。
6. 第三方行情SDK（AKShare等）只能做内部补数，**不能作为对外SaaS主数据源**。

# 为什么选MySQL，而不选PostgreSQL
先明确：**PG技术上完全可以做，不是PG不行，是结合你的业务、生态、运维、人才、周边工具、踩坑成本综合权衡的结果**。
你的业务：用户账号、付费、API‑Key、预警规则、私有公式、标的分组、告警简要记录，属于**OLTP业务库**，不是时序分析。

## MySQL优势（对你这个项目的实际收益）
### 1、运维人才、云生态、工具最普及
- 国内云厂商阿里云、腾讯云，MySQL托管实例、主从、读写分离、备份、监控、故障切换非常成熟。遇到问题网上资料极多，开发、运维人员对MySQL熟悉度远高于PG。
- 你后续上K8s，MySQL Operator、备份工具、binlog同步工具生态非常完善。
> PG云托管也有，但国内工程师实战经验储备整体弱于MySQL；出疑难问题，MySQL更容易找到解决方案。

### 2、你的业务模型，MySQL完全够用
你的业务表特征：
- 用户表、规则表、公式表、订阅表、订单表；单表千万以内。
- 主键查询、按user_id查询、少量联合查询；**没有大量复杂多表CTE、复杂递归、高级分析SQL**。
- 需要事务、读写分离、binlog（后续可做CDC同步，把业务规则同步到其他组件）。

MySQL InnoDB：事务、行锁、二级索引、主从复制，全部满足。
> 你不是要在业务库做复杂统计分析；统计分析交给Doris，业务库只做简单CRUD。

### 3、中间件生态丰富
- Sharding‑Sphere、MyCat，如果未来用户量暴涨，规则表需要分库分表，MySQL的分库分表中间件案例非常多。
- SpringBoot、MyBatis/MyBatis‑Plus，国内业务开发栈默认优先适配MySQL。

### 4、binlog CDC非常重要（对你的架构）
你现在：用户新增预警规则 → SpringBoot写MySQL，再发Kafka广播消息给Flink。
未来演进方案：可以直接消费MySQL binlog，自动把规则变更投递Kafka，**减少业务代码发消息，避免业务服务漏发消息带来的数据不一致**。
MySQL binlog生态成熟，Canal、Debezium大量生产案例。
PG也有逻辑复制，但是国内生产落地案例比MySQL少。

## PostgreSQL的优势，以及什么场景适合PG
PG强项：
1. 强大SQL能力：CTE、递归、复杂子查询、JSONB高级查询、自定义类型、自定义函数。
2. JSONB性能很强，如果大量存储半结构化JSON，PG更舒服。
3. 地理信息、复杂统计函数。

**哪些情况你应该选PG**：
- 业务有大量复杂SQL、递归查询；
- 大量非结构化JSON字段，频繁JSON过滤查询；
- 要在库内做大量计算。

### 你的项目，PG的短板（现实落地痛点）
1. JSONB很好，但你的规则、公式，建议是**结构化字段存储，不要塞大JSON**，发挥不出PG优势。预警规则拆成结构化表，而不是存一整个JSON blob。
2. PG逻辑复制CDC，Debezium也支持，但遇到版本升级、DDL变更坑比MySQL binlog多，生产踩坑案例少。
3. 国内运维工程师对PG调优、故障排查经验偏少；遇到锁、vacuum、膨胀问题，容易踩坑。
> PG最容易踩的坑：vacuum没配置好，表膨胀，磁盘暴涨，很多团队踩过。

## 关键澄清：不要混淆角色
> ❌不要拿PG去替代Doris做时序分析；
> ❌不要拿MySQL做时序K‑Line大表；

- MySQL / PG：只做OLTP业务库（用户、规则、订单）
- Doris：时序、筛选、统计分析。

> 如果你选择PG，架构也完全跑的通，功能上没有硬障碍，只是运维、生态、人才、国内落地案例不如MySQL。

## 结论，结合你的项目
1. **默认选MySQL 8.0，稳妥，生态成熟，踩坑少，CDC binlog对你规则同步很有用**。
2. 如果你团队本身所有人精通PG，经常用JSONB、复杂SQL，那直接上PG完全没问题。
3. 绝对不要把tick、K线这种时序数据放进MySQL/PG，这是OLAP库Doris的职责。

## 补充一个细节
很多人会想：PG的JSONB是不是适合存预警规则？
> 不建议。
预警规则：market、symbol、条件类型、阈值、冷却时间、公式id，这些是强结构化。拆成表，索引、查询、分页、过滤性能远好于JSONB。
只有当规则存在大量动态扩展字段，才考虑JSONB。你的场景结构化优先。

## 简单对比总结
|维度|MySQL|PostgreSQL|
|---|---|---|
|国内人才&云生态|⭐⭐⭐⭐⭐|⭐⭐⭐|
|事务、主从复制|成熟|成熟|
|CDC binlog/逻辑复制|大量生产案例|可用，但坑更多|
|复杂SQL、CTE、JSONB|一般|很强|
|Vacuum/表膨胀|几乎不用操心|需要重点维护|
|适配你的业务CRUD|完全够用|够用，能力过剩|

> 一句话：**你的业务没有用到PG的杀手锏特性，用MySQL成本更低风险更小；PG不是不行，是你的场景收益不明显，但运维成本更高。**

# 智能行情分析预警平台‑需求文档&技术方案
> 项目名称：智析平台
> 版本：V1.0
> 业务边界：**仅行情查看、自定义预警、AI智能选股筛选、标的分组、多渠道消息推送；不提供交易、不做买卖建议、不提供实盘下单**
> 支持市场：优先A股，架构预留港股、美股扩展能力；虚拟币仅架构预留，不对外上线。
> 终端入口：Web管理后台、微信公众号；对外开放付费API/SDK。

## 一、项目概述
### 1.1 项目目标
构建一套多市场行情数据平台，实现：
1. 实时、历史行情数据接入与存储；
2. 用户自定义条件预警（价格、涨跌幅、技术指标、自定义公式）；
3. 多渠道消息推送：公众号、邮件、Webhook、WebSocket；
4. AI自然语言聊天选股、智能条件筛选、标的分组管理；
5. 对外开放API与SDK，供第三方开发者调用；
6. 完整用户、权限、付费配额体系。

### 1.2 业务范围
✅包含：行情浏览、K线查询、指标查看、预警配置、私有公式管理、标的分组、AI对话选股、消息推送、开放API、后台管理。
❌排除：实盘交易、买卖点推荐、股票操盘指导、资金托管。

### 1.3 用户角色

### 4.3 核心消息Topic设计
1. `tick_raw_topic`：标准化tick消息，Protobuf，携带market、symbol、时间、价格、成交量；各市场网关统一写入该topic。
2. `rule_broadcast_topic`：用户预警规则变更广播流，Flink消费动态加载规则。
3. `alert_event_topic`：命中预警事件。
4. `notify_retry_topic`：推送失败重试队列。
5. `dead_letter_topic`：脏报文、处理失败消息。

### 4.4 核心数据流转
1. **实时行情&预警主链路**
行情源 → Go行情网关解析清洗 → Kafka tick_raw_topic
→ Flink消费tick：K线聚合、指标计算、匹配预警规则
  - 命中：输出alert_event_topic
  - 未命中：不输出告警，tick/K线继续写入Doris
  ‑ 更新Redis最新行情快照
→ Go notify‑service消费alert_event_topic，分发各类推送渠道。

2. **用户新增预警规则**
Web/公众号请求 → APISIX → SpringBoot业务服务
→ MySQL写入规则；同时发送规则变更消息到 rule_broadcast_topic
→ Flink消费广播流，动态加载规则，**无需重启Flink任务**。

3. **AI聊天选股链路**
前端请求 → APISIX → Python AI服务
→ 大模型将自然语言转为结构化筛选条件；条件合法性校验；
→ 组装Doris查询SQL执行筛选；
→ 查询返回标的列表，交给大模型润色自然语言回答返回前端。

4. **历史行情查询链路**
用户查询历史K线 → 业务服务查询Doris
  ①数据完整直接返回；
  ②检测时间片段空洞，投递任务到Celery补数队列后台拉取第三方数据写入Doris，完成后返回。

业务规则变更尽量通过Kafka广播流下发，尽量减少Flink任务重启发布。

# 完整技术选型（生产底座，支持1w‑100w用户、百亿数据）
> 每个组件写明：角色、为什么选、备选、上限、扩容方式。

## 1、行情接入层｜Go 自研行情网关集群
- 职责：对接各市场行情源websocket；多源容灾；协议解析；Protobuf标准化；脏数据过滤；输出Kafka。
- 语言：Go
- 部署：K8s无状态，按市场横向扩容；A股一组pod，港股一组pod，美股一组pod。
- 上限：单pod可以处理几十万tick/s；加pod即可扩容。
- ❌替代排除：不要用Python、不要让Flink直接连外部websocket。
> 关键点：网关只做网络协议转换，**零业务逻辑，零指标计算**。

## 2、消息总线：Apache Kafka集群
> 不选Redis‑Stream做生产主总线，Redis‑Stream不适合百亿级流数据长期堆积、分区弹性、大吞吐。Redis‑Stream只适合原型演示。
- Topic规划
1. `tick_raw_topic`：原始tick，按`market+symbol`做分区策略；分区数随吞吐可扩。
2. `rule_broadcast_topic`：预警规则变更广播。
3. `alert_event_topic`：告警命中事件。
4. `notify_retry_topic`：推送重试队列。
5. `dead_letter_topic`：脏数据、失败消息。
- 扩容：增加broker，增加分区；数据保留策略：热数据保留几天，原始tick流落盘到CK，Kafka不做永久存储。
- 备选：Pulsar；**仅当未来B端多租户重度、需要无限消息保存才切换**；现阶段Kafka生态更成熟，Flink深度集成，运维人才多。

## 3、实时计算层：Apache Flink Java
> 面对几百万用户预警规则、tick流、窗口计算，**Flink是该规模下最优解，不能替换为Go内存事件驱动**。
> Go事件驱动适合小体量；到达百万用户、几百万规则、晚到数据、窗口、状态持久化，自研事件驱动开发量巨大，bug风险极高。
- 职责：
  1. 消费tick_raw_topic；K线窗口聚合（1min/5min/日K等）
  2. TA‑Lib + 用户自定义公式AST执行；指标计算
  3. KeyedState(RocksDB)保存海量用户预警规则；消费rule_broadcast_topic动态更新规则，**尽量不重启Job**
  4. 规则匹配、告警防抖/防风暴；命中输出alert_event_topic
  5. 回流tick/kline数据输出到ClickHouse；更新Redis热点快照。
- 状态后端：RocksDB；开启增量checkpoint；Flink on K8s；状态可以横向扩缩容。
- 资源隔离：Flink独立资源namespace，CPU内存资源硬限制；AI/离线任务绝对不能抢占Flink资源。
- 备选：RisingWave；缺点是自定义公式AST执行支持弱，适合简单指标，不适合复杂用户自定义通达信类公式。

## 4、存储分层（重点，处理百亿tick数据）
### 4‑1 原始tick存储：ClickHouse集群
> tick写入量极大，写入吞吐优先，Join弱，适合存原始明细。
- 存储全部tick原始明细；按market、symbol、时间分区；TTL热冷策略；多年冷数据归档到对象存储S3。
- 定位：**原始数据底座，不直接面向前端业务查询**。
- 扩容：增加CK节点，水平分片。

### 4‑2 业务查询OLAP：Apache Doris集群
> Doris通过**外表映射ClickHouse**读取原始tick；内部存储聚合K线、财务、告警事件。
- 承担：AI选股批量筛选、历史K线业务查询、统计报表。
- 为什么这样组合（业界大规模量化平台标准方案）
1. CK扛疯狂tick写入压力；
2. Doris负责业务查询、多条件筛选、join元数据表；规避CK join短板。
- 扩容：增加DorisBE节点，水平扩分片。

> ❌不选择：TDengine、InfluxDB，多条件选股筛选能力不足。DuckDB只适合原型本地测试，不做分布式生产。

### 4‑3 OLTP业务库：MySQL 8.0集群
- 存储：用户、API‑Key、预警规则元数据、私有公式、标的分组、告警简要记录、权限、付费配额。
- 部署：主从读写分离；到达千万级后做分库分表 Sharding‑Sphere。
- CDC：Debezium消费MySQL binlog，同步规则变更，双保险，避免业务服务发Kafka漏消息。
- 不存任何tick、分钟K时序数据。
- 备选PG：团队精通PG可以替换，架构不变，只是生态人才成本更高。

### 4‑4 缓存层：Redis‑Cluster集群（多分片）
- 存储：热点标的最新tick、最新指标快照；限流、告警冷却、租户配额、高频AI筛选结果缓存。
- 热点标的做本地堆缓存（微服务内部Caffeine）二级缓存，击穿Redis压力。
> 只存热快照，绝对不存历史时序。

## 5、微服务层（K8s无状态，全部可以水平扩缩）
### 5‑1 业务核心服务 SpringBoot3 Java
用户管理、权限、付费配额、预警规则CRUD、公式管理、标的分组；写MySQL，发送规则变更到Kafka广播topic。
无状态，pod随便扩。

### 5‑2 Notify‑Service 推送分发｜Go
消费`alert_event_topic`；向外执行公众号、邮件、Webhook回调、WebSocket推送；重试、死信处理。
Go适合大量向外并发http客户端；无状态，压力上来直接加pod。

### 5‑3 AI查询服务 FastAPI Python
> NL2Query聊天选股；大模型转结构化条件，条件校验，组装Doris查询；结果润色。
- 重要隔离：**独立K8s资源池，和Flink实时计算资源物理隔离，防止AI查询打满CPU影响预警**。
- 增加高频条件缓存（Redis），减少大模型调用开销。
- 禁止大模型直接编造结果；所有筛选下推Doris。
- 无状态，QPS上涨直接扩pod。

### 5‑4 补数后台服务｜Python Celery集群
冷启动、Doris/CK数据空洞检测；调用开源SDK补历史K线；限流队列；**仅内部离线任务，不处理用户在线请求**。

# 完整数据流（大规模版本）

2. Flink消费tick_raw_topic：

# 关键取舍 & 为什么不选别的方案
1. **为什么不用Go自研流替代Flink？**
小规模可以；当几百万预警规则、百亿tick、晚到数据、窗口、checkpoint状态容错，自研流的开发、bug、稳定性成本极高。Flink是经过大厂验证的流计算底座，直接拿来用，把人力聚焦业务（公式解析、预警逻辑），而不是造流计算引擎。

2. **为什么CK+Doris外表组合，而不是单Doris？**
tick写入压力巨大，Doris写入能力不如ClickHouse；CK负责“疯狂写原始tick”；Doris负责“业务查询、Join、AI选股筛选”，各发挥所长。

3. **为什么不Pulsar替代Kafka？**
Kafka和Flink集成度最高，国内运维人才多；Pulsar优势是多租户和无限存储，你的场景收益不大，运维成本更高。

4. **为什么原型不使用Redis‑Stream？**
Redis‑Stream只适合演示；一旦流量上来，分区、吞吐、堆积能力远不如Kafka。**架构设计阶段就按Kafka设计；初期只是部署小规模Kafka集群，而不是换一套MQ。**

5. **AI服务必须物理资源隔离**
AI选股是重扫描OLAP查询，业务高峰期Doris查询压力会暴涨；如果和实时预警共享资源，会挤压实时链路，导致预警延迟、丢失。所以AI服务、Doris查询资源池与Flink实时计算资源池隔离。
