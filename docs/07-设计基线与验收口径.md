## 1. 冻结目标

本项目验证多源行情接入、流式计算、条件预警和实时推送在高可用、高性能、高并发场景下的工程可行性。主链路固定为：

```text
行情源 -> hq-gateway -> Kafka -> Flink -> alert_event -> notify(内嵌 alert-inbox) -> ws-gateway -> 客户端(ACK)
行情源 -> hq-gateway -> Kafka -> quote-push -> ws-gateway -> 客户端
行情源 -> Kafka -> ingest-worker -> ClickHouse
alert_event -> ingest-worker -> Doris(告警明细归档)
```

AI 筛选、补数、公式沙箱和非 WebSocket 渠道均不进入实时预警主链路。

## 2. 架构冻结项

| 领域 | 冻结决策 |
|---|---|
| 边缘入口 | APISIX 终止公网 TLS，负责路由、边缘限流和基础 JWT 校验 |
| WebSocket | ws-gateway 负责 WS 握手复核、业务授权、连接和投递；默认走 APISIX HTTP/2 或 HTTP Upgrade 代理，不采用未定义的 L4 透传鉴权混合模式 |
| 实时计算 | Flink 负责 K 线、指标、规则匹配和冷却状态，不直接写 ClickHouse |
| 行情扇出 | quote-push 独立消费 tick_raw，负责合并、快照和行情推送 |
| 告警投递 | notify 内嵌 alert-inbox 模块，处理 alert_event 的投递状态机（PENDING/SENT/ACKED/EXPIRED）、用户展开、重试和死信；ingest-worker 额外消费 alert_event 归档 Doris |
| 推送 Topic | 使用固定 64 分区的 `ws_push` Topic，通过 `gateway_slot` 路由；实例持有槽位租约并手动消费对应分区，禁止按实例动态创建 Topic |
| 规则同步 | RuleMsg 只广播规则，不携带 user_ids；用户订阅由业务库和 Redis 索引维护 |
| 时序存储 | ClickHouse 保存 tick/K 线明细；Doris 负责分析查询和筛选；MySQL 保存业务事务；Redis 保存热状态 |
| 扩展能力 | 通过 market 元数据增加市场，不修改公共消息结构和上层业务接口 |

## 3. 环境与资源口径

| 环境 | 资源 | 可验收内容 | 不承诺内容 |
|---|---|---|---|
| dev | 单机 Docker Compose | 功能闭环、接口契约、规则热更新、基础推送 | HA、百万连接、生产级吞吐 |
| benchmark-small | 10~15 台 8C16G 虚机 | 10 万 tick/s、10 万连接、100 万规则状态、核心故障恢复 | 100 万连接实测、百亿行冷查询 |
| benchmark-large | 最低 8 个专用 8C16G WS 节点 + 2 个 8C16G 压力源节点，数据平面独立部署 | 100 万 WS 连接、分级推送、重连风暴和连接层资源曲线 | 完整 OLAP 集群同时满载的端到端承诺 |

100 万连接是连接层的可水平扩展目标，不是 `benchmark-small` 的实测线。论文和交付报告必须分别标注“实测值”“设计目标”和“外推值”。

## 4. 用户规模演进阶段

用户规模只作为运营分档，节点扩容以峰值在线连接、tick 速率、告警速率和存储增长达到任一阈值为准。以下“在线连接”指峰值 WS 长连接数，“节点”指可独立扩容的计算/存储实例，不包含托管控制面。用户区间采用左闭右开，临界值归入后一阶段；`S1~S6` 保留给性能和混沌实验编号。

| 阶段 | 注册用户 | 峰值在线连接 | 推荐部署 | 主要目标 | 升级触发 |
|---|---:|---:|---|---|---|
| U0 启动期 | 0~1,000 | 0~100 | Compose 或 1~2 台虚机；MySQL/Redis/ClickHouse 单副本；Doris、Debezium、AI 可关闭 | 功能闭环、接口契约、行情落库、数据备份、基础监控 | 在线连接持续超过 100、单机 CPU/内存超过 70%、出现明显消息积压 |
| U1 内测期 | 1,000~5,000 | 100~300 | 3 台左右；APISIX 1、业务 2、WS 2；ClickHouse 单节点；Kafka/CK/Redis 可缩容混部；Doris/Debezium 可选 | 稳定运行、基础重启恢复、WS 重连和告警补拉 | 在线连接超过 300、tick 超过 3 万/s、Redis 内存超过 60% |
| U2 小规模生产期 | 5,000~10,000 | 300~1,000 | 4~6 台；Kafka 3 broker、Flink 2 JM HA + 2~4 TM（FC-1 修订，docs/09 V2.3 一致）、WS 2~3、Redis 主从、MySQL 主从、ClickHouse 基础副本；Doris 单节点可选；启用 Debezium 对账 | 基础 HA、限流、滚动发布、告警服务端不丢 | 在线连接超过 1,000、峰值告警超过 500/s、任一核心组件持续反压 |
| U3 增长期 | 10,000~100,000 | 1,000~10,000 | benchmark-small 规格；实时、推送、查询资源池隔离；WS 按连接数扩容 | 10 万 tick/s、10 万连接基线、故障演练、可观测性 | 在线连接超过 10,000、Kafka lag 持续增长、WS 单实例超过 15 万或出口超过 60% |
| U4 大规模期 | 100,000~1,000,000 | 10,000~100,000 | 独立 K8s 资源池；WS/Redis/压力源独立扩展；存储分片和归档 | 多 AZ、重连风暴、分级推送、水平扩展线性度 | 在线连接超过 100,000、单集群出口超过 70%、Redis 分片热点或规则状态恢复超时 |
| U5 超大规模验证期 | 1,000,000+ | 100,000+ | benchmark-large；6 个工作 WS 实例+2 个冗余实例起步，按槽位扩容 | 百万连接、连接层容量曲线、2 小时长稳和混沌验证 | 由实测结果和新增 ADR 决定，不按用户数自动扩展架构 |

### 4.1 阶段通用原则

1. U0~U2 可以减少副本、分区和节点，但不改变公共消息字段、Topic 名称、告警幂等、ACK/cursor 和服务职责。
2. U0~U1 不要求完整 HA；必须保留备份、健康检查、日志、指标和一键恢复流程。
3. U2 开始启用核心组件故障演练；U3 才进入 benchmark-small 的正式吞吐和连接验收。
4. U4~U5 的扩容优先作用于 ws-gateway、Redis、Kafka 分区和出口带宽，不把连接压力转嫁给 MySQL、Doris 或 ClickHouse。
5. 任何阶段若告警可靠性、数据一致性或安全边界不满足，不得通过增加节点掩盖问题，必须先修复对应链路。

### 4.2 MySQL 扩展策略

MySQL 初期不做水平分库分表。用户、规则、分组和告警投递状态的访问规模通常低于行情、WS 和 Kafka 链路，优先采用以下顺序：

```text
单主单库 -> 主从/高可用 -> 读写分离 -> 告警表按时间分区与归档 -> 垂直拆分 -> 水平分库分表
```

具体规则：

1. U0：单 MySQL 实例，使用索引、备份和可回滚迁移；不启用 Debezium。
2. U1：单实例 + 每日备份（scripts/backup/backup.sh），U2 起主从（FC-2 修订）；仍不分库分表。
3. U2~U3：`alert_record` 按 `trigger_at` 做月度或季度分区，并将超过 72 小时的投递状态归档；规则和用户表继续保持单库，便于事务和规则版本管理。
4. U4 以后：先按职责垂直拆分用户/规则库和告警投递库；只有单表数据量、写入 QPS、锁竞争或备份恢复时间达到阈值时，才新增 ADR 设计水平分片。

水平分片不得以 `user_id` 之外的随机键作为默认方案。若未来确需分片，用户和规则按 `user_id` 路由，告警投递按 `user_id` 与时间归档组合路由，并通过应用层生成全局 `delivery_id`；不能依赖跨分片自增主键、跨库 JOIN 或分布式事务。

## 5. WebSocket 与路由协议

### 5.1 连接状态

- ws-gateway 本地保存连接对象、订阅详情和发送队列。
- Redis 保存 `conn:{userId}` 到 `gateway_id` 的映射、订阅摘要和 TTL 心跳。
- 单实例按 20 万连接规划，`6 个工作实例 + 2 个故障冗余实例`作为百万连接目标拓扑。
- 行情消息允许丢旧保新；告警消息使用独立高优先级队列，不得被行情队列挤掉。

### 5.2 固定推送 Topic

> ws_push payload 含 QuoteBatch/AlertDelivery/**Kline**（proto oneof 既有；B21 起 Kline 闭合 bar 进入实时流，推 OneMsg 语义不变）。

`ws_push` 固定为 64 个逻辑槽位，分区键为 `gateway_slot`，消息同时携带 `gateway_id`。Redis 保存 `gateway_slot -> gateway_id` 的带版本租约；quote-push 和 notify 依据租约写入目标分区，ws-gateway 手动消费自己持有的分区。扩缩容只调整槽位租约和 drain 状态，不创建或删除 Topic；槽位数量不足时先扩充固定 Topic 的预留分区并通过 ADR 变更。

### 5.3 鉴权边界

公网 TLS 在 APISIX 终止，APISIX 执行边缘 JWT 校验；ws-gateway 在 Upgrade 阶段再次校验短期 access token 或 reconnect ticket，并执行用户、市场和标的授权。任何一层失败都关闭连接。reconnect ticket 只能用于短期重连，不替代业务授权。

## 6. 告警可靠性与补拉

### 6.1 标识与状态

- `event_id`：一次规则命中的全局事件，唯一键为 `rule_id + rule_version + trigger_window`。
- `delivery_id`：一次事件面向一个用户的投递，唯一键为 `event_id + user_id`。
- **alert-inbox 实现为 notify 内嵌模块**（不独立成服务、不独立消费组）：notify 消费 alert_event 后先幂等落库（PENDING，批量写、速率=事件速率，受 notify 消费速率整形），再推送并推进状态，写库失败进入 notify_retry 绝不丢。
- notify、ws-gateway 和客户端均按 `delivery_id` 幂等。
- **保留窗口 = 72 小时**（与 Kafka `alert_event` 3d 保留对齐）：alert_record 按日滚动清理；超窗未 ACK 的投递标记 EXPIRED；明细由 ingest-worker 归档 Doris，归档后仅支持离线查询、不支持在线补投。

### 6.2 投递流程

```text
Flink -> Kafka alert_event -> notify: alert-inbox 幂等落库(PENDING) -> 推送 ws_push -> client ACK(-> SENT/ACKED)
                                                      |-> notify_retry -> dead_letter
客户端重连 -> GET /alerts?cursor=... -> 返回未 ACK 且未过期的投递 -> 客户端去重并 ACK
```

服务端保证 Kafka 和 alert-inbox 保留窗口（72 小时）内不丢事件；客户端保证在该窗口内可通过 cursor 补拉。超过保留窗口的事件只保证已归档 Doris，不承诺在线补投。验收指标：

- 服务端事件丢失数 = 0；
- 保留窗口内可补拉投递数 = 100%；
- 重复投递可被 `delivery_id` 去重；
- 死信必须可观测、可重放、可审计。

## 7. 规则广播与订阅

RuleMsg 固定包含：`rule_id、version、op、market、symbol、rule_type、condition、cooldown_sec`。不得携带 `user_ids`。

Flink 只判断规则命中；notify 根据 MySQL 规则关系和 Redis 热订阅索引展开用户投递。规则版本按规则单调递增，Flink 丢弃旧版本；Debezium 只做周期对账和重发，不作为第二条实时下发通道。

## 8. 存储幂等

ClickHouse tick 和 K 线表必须包含 `event_id` 或等价的 `source_seq`，并设置 ReplacingMergeTree 版本列。ingest-worker 以 Kafka 批次和源事件键记录写入结果；重复消费不得产生业务重复记录。实时查询不得依赖 `FINAL` 才能满足核心延迟目标，去重策略必须在写入和查询模型中显式定义。

## 9. 最终验收线

| 类别 | benchmark-small | benchmark-large |
|---|---|---|
| tick 稳定吞吐 | 100,000/s，持续 30 分钟 | 100,000/s，持续 30 分钟 |
| 价格规则端到端延迟 | P99 < 2s | P99 < 2s |
| WS 连接 | 100,000，稳定 30 分钟 | 1,000,000，稳定 2 小时 |
| 活跃规则 | 1,000,000，版本对账一致 | 1,000,000，版本对账一致 |
| 故障恢复 | 单组件 MTTR < 5 分钟 | ws 实例故障后保留窗口（72h）内 100% 可补拉 |
| 告警可靠性 | 服务端丢失 0，保留窗口内可补拉 100% | 同左 |
| 查询 | Redis 命中 P99 < 10ms；冷查询单独记录 | 同左，独立记录资源曲线 |
