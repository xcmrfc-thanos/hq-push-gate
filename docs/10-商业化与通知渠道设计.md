# 商业化与通知渠道设计（通知渠道层 / 商业化层 / 开放平台层）

> 状态：设计稿（2026-09-07），实施分期见 §10；冻结契约（docs/04 §1/§2 proto/Topic/告警 ID 语义）零变更，
> 本设计全部落在"加表、加字段、加适配器、加鉴权模式"，不触碰冻结项。
> 业务规则来源：产品运营设计（套餐配额/渠道偏好/降级/熔断/开放平台），本文负责映射到 hq-push-gate 架构。

---

## 1. 定位与三层分解

| 层 | 内容 | 依赖 | 实施分期 |
|---|---|---|---|
| **L1 通知渠道层** | 邮件（阿里云 DirectMail）/短信适配器、服务商回调、退订闭环、渠道偏好降级、成本熔断 | notify 状态机（已有）+ Redis 熔断键位（docs/04 §5 预留） | 阶段 A（U1 后，**告警可靠性短板，最高优先**） |
| **L2 商业化层** | 套餐（free/vip1~3）、H5/API 共享配额、短信权限门控 | biz-service + user_vip 表（新增）+ alert_rule（已有） | 阶段 B（U2） |
| **L3 开放平台层** | accessKey 鉴权、WebHook 投递（签名/重试）、开发者 WS、事件报文 | ws-gateway（已有，加鉴权模式）+ notify（加 webhook 通道）+ api_developer_config（新增） | 阶段 C（U2 后半） |

**核心判断**：核心告警链路（Flink 规则匹配 → alert_event → ws_push → 补拉）已实现且强于外部方案
（对方"WS 断线不补发靠客户兜底"，本系统为 Kafka 持久化 + 72h 补拉，商业化时这是分级服务能力）。
本设计不重建链路，只在其上加"渠道"与"商业"两层。

## 3. 套餐与配额（L2）

### 3.1 套餐档位（产品口径，硬编码于业务层，DB 可覆盖）

| 用户类型 | H5 页面订阅上限 | 开放 API 订阅上限 | 短信权限 | 渠道偏好 |
|---|---|---|---|---|
| 免费 free | 5 | 20 | ❌ 不可用 | 仅邮件 |
| vip1 | 10 | 50 | ✅ | 可选 优先短信/优先邮件 |
| vip2 | 20 | 100 | ✅ | 可选 |
| vip3 | 50 | 300 | ✅ | 可选 |

- 配额单位 = **生效的 alert_rule 数**，**双闸校验（方案 b，2026-09-11 定稿）**：
  - **入口闸**：`count(source=h5) ≤ h5_max_sub`、`count(source=api) ≤ api_max_sub`——两入口互不侵蚀（H5 用满 5 不占 API 额度，反之亦然）；
  - **总量闸**：`count(全部活跃) ≤ h5_max_sub + api_max_sub`——混合使用总量有界（free 25 / vip1 60 / vip2 120 / vip3 350）；
  - 废弃原"合并统计对单入口上限"口径：混合使用时有效上限=max(两档)，会使低档入口（H5 的 5 只）形同虚设；
  - 原"防两入口叠加绕过"诉求由入口闸天然保证：任一入口都无法超过自身档位。
- 前端仅展示，**校验只在 biz-service 后端**（两入口统一经 APISIX → biz-service，架构天然防绕过）；
- 免费用户 API 给 20 只 > H5 的 5 只：面向开发者的获客设计，但**短信权限一律关闭**，保护短信成本。

### 3.2 配额校验流程（POST /rules 与 POST /api/v1/alarm/subscribe 共用）

```text
1. 鉴权（JWT / accessKey）→ 解析 user_id
2. 读 user_vip（Redis 缓存 user_vip:{id}，TTL 5min；未命中回源 MySQL）
3. 分组计数：count(alert_rule where user_id=? and status=1 group by source)（h5 / api 两桶）+ 总数
4. 双闸校验（任一不过 → 400 "超出当前套餐最大订阅数量"）：
   入口闸：source 计数 + 本次新增(1~2 条) <= 对应档位（h5→h5_max_sub / api→api_max_sub）
   总量闸：总数 + 本次新增 <= h5_max_sub + api_max_sub
5. 免费 user + channel_prefer=sms → 400 拒绝
6. 校验 stock_code/symbol 合法性（symbol_meta 存在性）
7. 写入 alert_rule（source=h5|api）→ outbox → rule_bcast 热更新（既有链路）
```

> 代码对齐注记：现实现为合并计数对单入口上限（原口径），双闸改造属小改
> （RuleService/SubscribeService 计数 SQL 加 group by source + 一次总数查询），随下一代码批次落地。

### 3.3 订阅模型映射（关键设计：subscribe 是 alert_rule 的糖衣）

`POST /api/v1/alarm/subscribe` 入参（产品口径）：

```json
{
  "stockCode": "600000",
  "riseThreshold": 0.05,
  "fallThreshold": -0.05,
  "channelPrefer": "sms | email"
}
```

内部映射（**不扩展 RuleType 枚举，无 ADR**）：

| 入参 | 生成 alert_rule |
|---|---|
| riseThreshold>0 且 fallThreshold<0 | 一条 `PCT_CHANGE`，condition=`{"threshold":0.05,"direction":"both"}`（涨跌幅绝对值，既有语义） |
| 仅 rise>0 | 一条 `PCT_CHANGE`，condition=`{"threshold":0.05,"direction":"up"}` |
| 仅 fall<0 | 一条 `PCT_CHANGE`，condition=`{"threshold":0.05,"direction":"down"}` |
| 绝对价格（可选扩展） | `PRICE_ABOVE`/`PRICE_BELOW`，threshold=价格 |

- `direction` 为 condition JSON 内新增键，Flink RuleMatchFunction 解析适配（纯代码，不动 proto）；
- `channelPrefer` 落 alert_rule 新列（见 §8），空则继承 user_vip.channel_default；
- 订阅删除 = alert_rule status=0（停用），DELETE /api/v1/alarm/subscribe?subscribeKey= 按订阅标识停用（代码 SubscribeController 退订按 subscribeKey，非 stockCode）。

### 3.4 行情权益矩阵（B22，ADR-040 落地）

WS 行情通道按 `user_vip.plan_type` 门控与差频（quote 合并帧 per-conn，丢旧保新天然支持长间隔）：

| 用户类型 | quote 合并帧间隔 | kline 周期档位 |
|---|---|---|
| free | **10s**（降频） | 仅 `kline@1m` |
| vip1~vip3 | **3s**（quote@3s 默认契约） | `kline@1m/3m/5m/15m/30m/60m/1d` 全周期 |

- **数据源**：Redis `user_vip:{id}`（值 `planType|expireEpochSec`，TTL 5min；expire 已过按 free）。biz-service 写路径同步（grant / 到期降级 / planOf 回填），ws-gateway 只读 Redis 免打库（ADR-040）；
- **sub 门控**：free 订阅 `kline@3m+` 的 channel 被忽略（权益白名单）；vip 全开放；`quote@3s` 是默认行为，free 实际按 10s 合并帧下发；
- **复核**：ws-gateway 每 `ENTITLE_RECHECK`（默认 5min）按在线 user_id 复核，降级/封号后存量连接**下一复核周期内**降档（差频 10s）并摘除越权 kline 周期（ADR-040 语义）；
- **亚分钟口径**：3s/10s 仅实时流，不落 CK（与 ADR-041 一致）。

## 4. 通知渠道层（L1）

### 4.1 投递决策器（notify 消费 alert_event 后新增的步骤）

```text
alert_event → 查 user_vip + alert_rule.channel_prefer → 决策：

【优先短信】
  allow_sms=1 且 全局短信日额度未熔断 且 用户短信日额度未满 且 服务商健康（定义见 §4.3）
    → 短信 + 邮件（邮件为同步备份留存，永远发）
  任一不满足 → 仅邮件（自动降级）

【优先邮件】
  仅邮件；
  振幅达重大阈值（后台配置，如 |pct| >= 9.8%）
    → 尝试补发短信（仍受熔断限制，且仅当 allow_sms=1——free 用户一律不补发）
```

要点：**"优先短信"≠100% 短信**；邮件永远是兜底通道，保证告警不丢。

### 4.2 通道适配器（notify 内新增 infrastructure 适配器，接口统一）

```go
type Channel interface {
    Send(ctx context.Context, msg OutboundMessage) (providerMsgID string, err error)
}
// 实现：mailAdapter（阿里云 DirectMail HTTP API）、smsAdapter（短信服务商）、
//      webhookAdapter（开发者回调，L3）
```

- 每次投递写 `notify_send_log`（§8）：user_id、rule_id、channel、provider_msg_id、状态、错误；
- 失败走 notify 既有重试（notify_retry）与死信（dead_letter）链路，零新机制。

### 4.3 成本熔断与单用户限额（Redis，rl: 键位）

| 键 | 语义 | 到达后行为 |
|---|---|---|
| `rl:mail:daily:{yyyyMMdd}` | 邮件全局日发送量（INCR+当日过期） | 停止邮件，告警日志（已短信熔断时：**告警事件仅落 inbox 等补拉**） |
| `rl:sms:daily:{yyyyMMdd}` | 短信全局日发送量 | **关闭短信通道，全部用户降级邮件**（server_notice 广播给开发者） |
| `rl:sms:user:{uid}:daily:{yyyyMMdd}` | 单用户短信日上限 | 该用户降级邮件 |
| `rl:mail:user:{uid}:daily:{yyyyMMdd}` | 单用户邮件日上限 | 该用户静默（inbox 仍可补拉） |

阈值来自 env（NOTIFY_MAIL_DAILY_LIMIT 等），运营后台可调（本期 env，后台界面后续批次）。

**服务商健康判定（§4.1 决策树的"服务商健康"输入，2026-09-11 补定义）**：
以 `notify_send_log` 为事实源——某 channel 近 5 分钟发送 ≥10 条且失败率 >50% → 该 channel
熔断 300s（Redis 共享态，复用 LLM 网关 circuit 模式），熔断期间该渠道请求按上表降级，
冷却到期自动恢复探测。

**IM / 开发者 WebHook 降级矩阵（补全）**：

| 通道 | 失败行为 |
|---|---|
| dd / feishu 群机器人 | notify_retry 链路内重试耗尽 → 降级邮件 + send_log 记 DEGRADED（仅该用户 channel_default=dd/feishu 时生效） |
| 开发者 webhook（L3） | 不参与日额熔断；失败走 notify_retry → dead_letter（出站 HMAC/防重放见 §6.3），由开发者侧对账 |

### 4.4 退订闭环

邮件模板自带退订链接（DirectMail 捕获）→ EventBridge 回调（§5）→
`dm:Feedback:Unsubscribe` → 该 user 全部 alert_rule `status=0`（停用，可恢复）→
生成 `user_unsubscribe` 事件推送开发者（L3）→ 投递侧即时的 inbox 记录保留（供审计）。

## 5. 服务商回调（服务商 → 本系统，HTTP WebHook）

### 5.1 入口

| 回调 | 路径（APISIX 公网 HTTPS，免 JWT 但带签名校验） | 处理 |
|---|---|---|
| EventBridge 邮件事件 | `POST /internal/hooks/dmail`（APISIX 路由单独放行+IP 白名单） | 验签 → 同步落 notify_send_log（回执量级低，**不进 MQ，U0-U2 无需新 Topic/ADR**；>100/s 再评估新 Topic 届时走 ADR） |
| 短信回执 | `POST /internal/hooks/sms` | 验签 → 落库 |

原则：hook 入口只做**验签 + 参数校验 + 落库**，重业务（退订展开等）异步 goroutine；
200 快速返回，服务商重试策略不冲突。

> **崩溃窗口与兜底（2026-09-11 补）**：200 之后进程崩溃会丢失该条事件的处理——普通投递回执
> 可接受（下一条事件自愈）；**退订类事件（dm:Feedback:Unsubscribe、短信回执退订）必须同步幂等
> 落库后再 200**（单行 INSERT 代价可接受），否则"用户已退订仍继续发信"属合规敏感故障。
> 兜底依赖服务商侧重试：EventBridge 投递失败按退避至少重试 3 次（服务商控制台可配），
> 接入验收时须确认该配置已开启。

### 5.2 关键事件

```json
{"source":"dm.aliyuncs.com","type":"dm:Deliver:Succeed","data":{...}}   // 投递成功
{"type":"dm:Deliver:Fail"}                                              // 退信/失败
{"type":"dm:Feedback:Unsubscribe"}                                      // 邮件退订（删全部订阅）
```

## 6. 开放平台（L3，面向 API 开发者）

### 6.1 接入模型

- 开发者在 user 体系注册 → 分配 `access_key` + `app_secret`（api_developer_config）；
- 订阅/查询 REST：**AK/SK 签名鉴权**（`/open/v1/*`，docs/11 §5——`X-Signature=HMAC-SHA256(...)` + timestamp ±300s + nonce 防重放；**不使用裸 `Bearer accessKey`**，B18 已实装）；
- 事件推送二选一：**WS 长连接**（复用 ws-gateway，**60s 一次性 ticket**，禁止 `?accessKey=` 直连防 AK 进日志，docs/11 §5.2）或 **WebHook**（notify webhookAdapter，v2 签名）。

### 6.2 开发者 WS（复用 ws-gateway）

- 地址 `wss://<domain>/ws?ticket=<60s 一次性票据>`：先经 `/open/v1/ws-ticket`（AK/SK 签名）换票，
  ws-gateway TicketAuth 取票后换 user_id 并即焚（B18 已实装；原设计的裸 accessKey 分支弃用）；
- 推送链路**完全复用**：alert_event → notify 决策 → 路由 ws_push 槽位 → SlotConsumer → hub 下发；
- 事件 JSON（服务端输出层组装，不改 proto；AlertEvent.detail_json 携带扩展字段）：

```json
{"eventType":"alarm_event","eventId":"...","userId":"api_user_001","source":"api",
 "subscribeId":123,"stockCode":"600000","price":10.23,"changeRate":0.062,
 "alarmType":"rise","threshold":0.05,"triggerTime":"...","channel":"sms+email",
 "smsSendOk":true,"emailSendOk":true}
```

另有 `subscribe_changed`（可选开）、`user_unsubscribe`（必推）、`server_notice`（熔断广播）。

### 6.3 WebHook 投递（webhookAdapter）

- POST hook_url，头：`X-Hook-Sign: sha256=HMAC(app_secret, ts.nonce.SHA256(body))`（**v2 防重放**，B18 实装，docs/11 §5.3）、`X-Hook-Timestamp`、`X-Hook-Nonce`、`X-Hook-Version: 2`、`X-Event-Type`、`X-Request-Id`；
- 2xx 成功；非 2xx 重试 3 次（2s/5s/10s，复用 notify_retry）；耗尽落库供查询，**不阻塞主流程**；
- 断线/失败不补推，开发者用 `GET /alerts?cursor=` 补偿（已有接口，文档引用）。

## 7. 接口契约（新增/调整，均走 APISIX 边缘）

| 接口 | 说明 | 鉴权 |
|---|---|---|
| `POST /api/v1/alarm/subscribe` | 创建订阅（糖衣，映射 alert_rule，§3.3） | JWT（AK/SK 面在 /open/v1，docs/11 §1.1） |
| `DELETE /api/v1/alarm/subscribe` | 按 subscribeKey 停用订阅（SubscribeController `@RequestParam subscribeKey`） | 同上 |

## 8. 数据模型变更（迁移实况与草案）

### 8.1 V3（已实施，`migrations/mysql/V3__channels_and_vip.sql`）

```sql
-- 用户套餐（与 user 1:1；plan_type: free/vip1/vip2/vip3）
CREATE TABLE user_vip (
  user_id          BIGINT PRIMARY KEY,
  plan_type        VARCHAR(16) NOT NULL DEFAULT 'free',
  expire_time      DATETIME NULL,
  h5_max_sub       INT NOT NULL DEFAULT 5,
  api_max_sub      INT NOT NULL DEFAULT 20,
  allow_sms        TINYINT NOT NULL DEFAULT 0,
  channel_default  VARCHAR(8) NOT NULL DEFAULT 'email',   -- sms|email|dd|feishu
  dingtalk_webhook VARCHAR(512) NULL,   -- 钉钉机器人绑定：URL[|加签secret][|关键词]
  feishu_webhook   VARCHAR(512) NULL,   -- 飞书机器人绑定：同上
  updated_at       DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

ALTER TABLE `user` ADD COLUMN email VARCHAR(254) NULL UNIQUE;  -- H5 默认邮箱/退订反查键

ALTER TABLE alert_rule
  ADD COLUMN channel_prefer VARCHAR(8) NULL COMMENT 'sms|email|dd|feishu，NULL=继承套餐',
  ADD COLUMN source         VARCHAR(8) NOT NULL DEFAULT 'h5' COMMENT 'h5|api',
  ADD COLUMN subscribe_key  VARCHAR(64) NULL,
  ADD KEY idx_source (source);

CREATE TABLE notify_send_log (
  id              BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id         BIGINT NOT NULL,
  rule_id         BIGINT NOT NULL DEFAULT 0,
  event_id        VARCHAR(64) NOT NULL DEFAULT '',
  channel         VARCHAR(8) NOT NULL,             -- mail|sms|webhook
  provider        VARCHAR(32) NOT NULL,
  recipient       VARCHAR(320) NOT NULL DEFAULT '',
  provider_msg_id VARCHAR(128) NULL,
  status          VARCHAR(16) NOT NULL,            -- SENT|FAIL|DEGRADED|UNSUBSCRIBED
  error           VARCHAR(512) NULL,
  created_at      DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY idx_user_time (user_id, created_at),
  KEY idx_event (event_id),
  KEY idx_recipient (recipient)
);

-- 自检修复：alert_record.id 无自增导致 notify 落库静默丢弃（V3 迁移已加 AUTO_INCREMENT，migrations/mysql/V3__channels_and_vip.sql）
ALTER TABLE alert_record MODIFY id BIGINT NOT NULL AUTO_INCREMENT;
```

## 9. 安全与风险（吸收外部设计坑点 + 本架构补充）

1. 配额校验只在 biz-service 后端；H5/API 共享 `count(alert_rule)` 防两入口叠加绕过；
2. "优先短信"必须降级（§4.1），防行情集体异动打爆短信账单；免费用户短信权限硬关闭；
3. WebHook/回调必须验签（HMAC）；开发者 app_secret 流水线注入，仓库零凭据；
4. 回调入口 APISIX 单独路由 + 来源 IP 白名单，与业务 API 隔离；
5. 邮件文案强制风险提示、自带退订；短信带 TD 退订（合规）；
6. WS 离线消息语义：开发者 WS 不补发（付费开发者可用 /alerts 补拉窗口分级——本系统已有能力，作增值卖点）；
7. 邮件/短信服务商凭据仅 env/密钥服务；仓库与示例零凭据字面量。

## 11. 订阅规则类型体系（选股/告警规则全量设计）

> 设计原则：
> 1. **proto RuleType 冻结枚举（5 个）不扩展**——所有新类型映射到既有枚举 + condition JSON 参数化；
>    `INDICATOR` 枚举本就预留，时序/指标类全部落入它，无需 ADR（condition 是 string 装 JSON）。
> 2. 每个类型 = `condition JSON schema` + 触发语义 + 数据依赖 + Flink 匹配要点 + 防抖建议。
> 3. 分三批落地：T0=现有 tick 流即可；T1=需日线宽表；T2=需指标算子/新数据源。

### 11.0 通用 condition 公共字段（所有类型可叠加）

| 字段 | 类型 | 说明 |
|---|---|---|
| `direction` | up/down/both | 涨跌方向过滤（PCT_CHANGE 用；up=只报涨） |
| `once` | bool | 触发一次后自动停用（目标价提醒场景；权威撤销 = bcast DELETE，不用 Flink 状态，见 §11.8） |
| `session` | open/close/all | 生效时段（默认 open=仅盘中） |
| `expire_at` | int64 | 订阅有效期（毫秒），过期 Flink 侧丢弃 |

> Flink 实现注意：`once` 需要 keyBy(symbol+rule) 后的 keyed 状态做"已触发"标记（MapState，TTL=当日）。

### 11.1 T0 批：tick 实时可算（Branch 13，1~2 周）

| # | 类型（用户语义） | 枚举映射 | condition schema | 触发语义 | 防抖 |
|---|---|---|---|---|---|
| 1 | 价格涨至/突破 | PRICE_ABOVE | `{"threshold":12.5}` | 最新价 > 阈值 | cooldown 已有 |
| 2 | 价格跌至/跌破 | PRICE_BELOW | `{"threshold":9.8}` | 最新价 < 阈值 | 同上 |
| 3 | 进入价格区间 | PRICE_RANGE | `{"low":10,"high":12}` | 落入 [low,high] | 同上 |

### 11.7 双引擎评估架构（设计决策）

28 种规则按数据节奏拆成**两个评估引擎**，避免实时路径扛不动日频语义：

| 引擎 | 规则 | 数据 | 触发 |
|---|---|---|---|
| **实时引擎**（现有 Flink TickRuleJob 扩展） | T0 批 11 种（tick 双字段可算） | tick_raw 流 | 逐 tick |
| **日频引擎**（收盘批量评估作业，Branch 14 新增） | T1 批 12 种（MA/量比/新高/连涨等） | stock_daily 宽表 + INDICATOR 规则表 | 每交易日收盘后一次 |

决策理由：
1. T1 的基线（均量/MA/前高）需要历史窗口——Flink 实时路径逐 tick 读 Redis 基线在 10 万 tick/s 下不可行；
2. 日频规则的语义本来就是"收盘确认"，批量评估零状态、可重放、实现成本为 Flink 路径的零头；
3. 批量评估直接产出冻结契约的 alert_event 进 Kafka，渠道层（notify）/WS 通知全链路复用，零改动。

落点：批量评估作业 U0-U1 以脚本形态（scripts/daily/，与对账脚本同模式）；U3+ 转 K8s CronJob。

**stock_daily 宽表**（CK，Branch 14）：`ReplacingMergeTree(ingest_version) ORDER BY (market, symbol, date)`，
列：date、OHLC、pre_close、pct_chg、volume、amount、amplitude、vol_ma5、vol_ratio、high_20d、low_20d、consec_up_days、consec_down_days。
来源：kline_local 1m 收盘聚合 + 东财日线对账修正；派生列（量比/连涨天数）由日批任务回填。

### 11.8 once 自动停用闭环（复用退订机制）

`once:true` 的规则触发后必须自动停用（目标价场景）。方案：**notify 消费 alert_event 后检查
condition.once → 停用规则（status=0）→ 向 rule_bcast 发 DELETE（复用退订已建机制）**。
> 设计注记（2026-09-08 成文）：退订/once 停用的 rule_bcast DELETE 由 notify 直发（RuleBcastPublisher，
> hooks.go 既有实现，退订闭环依赖）——属补偿性副作用（幂等 DELETE、低频），不经过 outbox_event
> （outbox 保业务写入原子性；撤销事件由停用动作触发，直发不破坏一致性）。
- 不用 Flink 状态做 once：作业重启丢状态会重复触发；bcast DELETE 才是权威撤销；
- 触发到 DELETE 传播之间的重复告警由 cooldown_sec（默认 60s）吸收，可接受；
- 用户重新激活 = 重建规则（新 version），既有链路无感。
