# hq-push-gate 最终规划与技术选型

> 版本：V2.3 设计收敛版
>
> 本文是面向实施的最终规划总表。它不替换 `00~08` 的详细约束，而是将用户增长阶段、组件启用顺序、同品种选型理由、生产补强项和实施门禁集中收口。若本文与冻结基线冲突，以 `07-设计基线与验收口径.md` 为准，并通过新增 ADR 变更。

## 1. 最终架构结论

主链路固定为：

```text
行情源 -> hq-gateway -> Kafka -> Flink -> alert_event -> notify/alert-inbox -> ws-gateway -> 客户端 ACK
行情源 -> hq-gateway -> Kafka -> quote-push -> Redis/固定 ws_push -> ws-gateway -> 客户端
行情源 -> Kafka -> ingest-worker -> ClickHouse
alert_event -> ingest-worker -> Doris
业务事务 -> MySQL + Outbox -> Kafka rule_bcast -> Flink
```

最终采用“逻辑生产架构不变、物理资源按阶段缩放”的原则：几百用户不部署完整大集群，但从第一天就保留公共 Topic、消息字段、幂等 ID、ACK/cursor、备份和观测接口，避免后续换协议、换链路或重写核心服务。

核心职责边界如下：

| 领域 | 最终组件 | 不承担的职责 |
|---|---|---|
| 公网入口 | APISIX + LB/CDN | 不承载业务事务和 WS 连接状态 |
| 行情接入 | hq-gateway | 不做规则计算和用户投递 |
| 实时事件总线 | Kafka | 不作为业务数据库，不用 RabbitMQ 并行承载同类事件 |
| 流计算 | Flink | 不直接写 ClickHouse/Redis，不展开 user_ids |
| 行情快照 | quote-push + Redis | 不负责告警可靠投递 |
| 告警投递 | notify 内嵌 alert-inbox | 不让客户端直接消费 Kafka |
| 长连接 | ws-gateway | 不查询 MySQL 承担用户业务编排 |
| 事务数据 | MySQL | 不存 tick 明细和海量分析结果 |
| 明细时序 | ClickHouse | 不作为事务库和全文检索库 |
| 分析查询 | Doris | 不进入实时告警热路径 |

## 2. 用户阶段与最终部署规划

用户数只是运营指标，扩容以峰值在线、tick/s、告警/s、Kafka lag、Redis 内存、出口带宽和恢复时间任一项先达到阈值为准。阶段采用左闭右开区间。

| 阶段 | 用户/峰值在线 | 组件部署 | 这一阶段必须完成 |
|---|---|---|---|
| U0 启动期 | 0~1,000 / 0~100 | Compose 或 1~2 台虚机；Kafka/Flink/Redis/MySQL/CK 单实例；Doris、Debezium、AI 可关闭 | 核心闭环、Outbox、备份、健康检查、Prometheus、结构化日志、基础限流 |
| U1 内测期 | 1,000~5,000 / 100~300 | APISIX 1~2、业务 2、WS 2；Kafka/Redis/CK 可缩容混部；**MySQL 单实例 + 每日备份（FC-2 决策，U2 起主从）** | 滚动发布、WS 重连、告警补拉、死信重放、租约续期、恢复演练 |
| U2 小生产 | 5,000~10,000 / 300~1,000 | Kafka 3 broker RF=3；Flink 2 JM HA + 2~4 TM；Redis 主从/小 Cluster；MySQL 主从；Debezium 对账；Doris 按需启用 | 单组件故障恢复、Schema 兼容检查、ACL、checkpoint/savepoint、读写分离 |
| U3 增长期 | 10,000~100,000 / 1,000~10,000 | 实时、推送、查询、离线资源池隔离；CK 2 分片×2 副本；Doris 3 FE+3 BE；WS 按连接扩容 | 10 万 tick/s、10 万连接、百万规则、混沌演练、SLO 和容量自动告警 |
| U4 大规模 | 100,000~1,000,000 / 10,000~100,000 | 多 AZ K8s；WS、Redis、Kafka、出口带宽独立资源池；CK/Doris 分片归档 | 重连风暴、分级推送、租约 fencing、跨 AZ 备份和恢复 |
| U5 超大规模 | 1,000,000+ / 100,000+ | benchmark-large；6 个 WS 工作实例+2 个冗余实例起步，按固定槽位扩容 | 百万连接 2 小时长稳、故障切换、带宽曲线、容量外推报告 |

扩容顺序固定为：

```text
业务副本 -> ws-gateway -> Redis 分片 -> Kafka 分区/代理 -> quote-push/notify -> 出口带宽 -> CK/Doris
```

MySQL 不在行情和 WS 热路径。U0~U3 不默认分库分表，采用单库、主从、读写分离、告警表时间分区、归档；U4 以后先垂直拆分，只有出现锁竞争、单表容量、写入 QPS或恢复时间瓶颈，才新增 ADR 按 `user_id` 分片。

## 3. 同品种技术选型理由

### 3.1 消息总线：Kafka，不选 RabbitMQ

| 方案 | 适合点 | 本项目判定 |
|---|---|---|
| Kafka | 高吞吐追加日志、分区并行、消费组、保留和 offset 重放 | **主选**。tick 需要多组独立消费，Flink/入库/行情扇出均可重放 |
| RabbitMQ | 低延迟任务队列、复杂路由、单次消费 | 不作为实时主总线。百万 tick、多消费组和长保留不如 Kafka 直接 |
| Pulsar | 存算分离、多租户、跨地域场景 | 当前不选。架构能力强，但运维和论文项目复杂度高于收益 |
| Redis Streams | 本地原型简单 | 仅可做开发期替代，不满足正式吞吐、重放和分区验收 |

结论：只保留 Kafka 一条实时事件总线；邮件、补数等任务如未来需要队列，先使用 Kafka 独立 Topic，出现明确任务型路由需求再单独评估 RabbitMQ。

### 3.2 流计算：Flink，不选 Kafka Streams/Spark Streaming

Flink 对事件时间、watermark、窗口、广播规则、RocksDB 状态、checkpoint/savepoint 和迟到数据处理最完整，适合“行情窗口 + 指标 + 百万规则 + 防抖”组合场景。Kafka Streams 适合嵌入式轻量拓扑，但规则状态和作业生命周期管理不如 Flink；Spark Streaming 更偏批流一体，端到端低延迟和状态恢复路径更重。

### 3.3 明细与分析：ClickHouse + Doris，不选单一产品

| 方案 | 优势 | 判定 |
|---|---|---|
| ClickHouse | 高频批量写、列式压缩、时序聚合和物化视图强 | **明细主存储**，承载 tick/K 线 |
| Apache Doris | MySQL 协议、MPP Join、并发分析和业务查询友好 | **分析查询层**，承载告警统计和 AI 筛选 |
| StarRocks | 向量化和 Join 能力强 | 备选；仅当 S4 查询 P99 不达标时通过 ADR 切换 |
| Elasticsearch | 全文检索、日志搜索 | 当前不引入；日志已有 Loki，标的搜索暂由 MySQL/Redis 覆盖 |
| TDengine/InfluxDB | 设备时序和标签模型强 | 不适配金融多维筛选、Join 和分析模型 |

结论：CK 与 Doris 是职责分层，不是重复部署。Doris 不承接 tick 高频写入，CK 不承担复杂业务 Join。

### 3.4 缓存：Redis Cluster，不选 Memcached/本地缓存单独承担

Redis 提供 TTL、Lua/事务、集合结构、订阅索引、限流计数、租约和 Cluster 分片，能同时满足热快照、订阅关系、连接路由和冷却状态。Caffeine 只作为进程内一级缓存，不能替代 Redis 的跨实例状态；Memcached 无持久化、集合语义和租约能力，不适合本项目。

### 3.5 业务库：MySQL，不提前分库分表

MySQL 的事务、生态、迁移工具和团队可维护性最适合用户/规则/订阅/inbox 元数据。主从、读写分离、时间分区和归档足以覆盖 U0~U3。过早分片会引入全局 ID、跨库查询、CDC 路由、分布式事务和恢复复杂度；分片是容量实测后的最后一级扩展，不是用户数达到某个数字就自动启用。

### 3.6 可观测：Prometheus + Grafana + Loki + OTel/Tempo + pprof/Pyroscope

| 信号 | 主选 | 作用 |
|---|---|---|
| Metrics | Prometheus + Grafana + Alertmanager | QPS、P99、lag、checkpoint、连接数、带宽、SLO |
| Logs | Loki | 结构化日志、低成本保留、与 Grafana 联动 |
| Traces | OpenTelemetry Collector + Tempo | Go/Java/Python/ Kafka 统一链路追踪 |
| Profiles | Go pprof + Pyroscope；Flink 使用 JVM/async-profiler | CPU、内存、锁、GC 和火焰图 |
| APM 替代 | SkyWalking | 仅已有 SkyWalking 运维能力时替代 Tempo，不与 Tempo 默认双建 |

Prometheus 不做日志，Loki 不做指标，Tempo 不做 Profiling；工具职责不混用。必须限制高基数 label，禁止将 `user_id`、`symbol` 等无界值直接作为 Prometheus label。

### 3.7 网关与编排：APISIX + K8s

APISIX 负责公网 TLS、JWT、限流、路由和 Upgrade 代理；ws-gateway 负责连接、业务授权和背压。K8s 负责无状态服务自愈、PDB、反亲和、HPA 和滚动发布；Kafka/Flink/CK/Doris/MySQL/Redis 使用 Operator 或托管服务，避免把有状态故障逻辑散落到业务代码。

## 4. 生产级必备补强项

以下能力是“高可用、高性能、高并发项目”的交付门槛，不因 U0 资源缩小而删除，只允许降低部署规模：

1. **一致性**：MySQL Outbox、Kafka 幂等生产、Schema 兼容检查、Topic ACL；
2. **恢复**：MySQL/Kafka/Redis/CK/Doris 备份、跨 AZ 副本、RPO/RTO、定期恢复演练；
3. **Flink**：外部 checkpoint、savepoint 发布、状态 TTL、watermark/迟到数据和回滚；
4. **推送**：gateway_slot 租约 TTL、续租、fencing token、drain、旧实例隔离和重连限速；
5. **流量保护**：入口限流、租户/用户配额、队列水位、熔断、降级、死信和重放；
6. **安全**：Secret 外置和轮换、最小权限、Kafka ACL、数据库账号分权、WSS、审计日志和脱敏；
7. **交付**：CI 单测/契约测试/集成测试、镜像扫描、SBOM、灰度、自动回滚、数据库迁移回滚；
8. **运维**：Runbook 覆盖 Kafka lag、Flink checkpoint、Redis 切换、MySQL 故障、CK 写入失败、死信增长和重连风暴；
9. **数据治理**：保留周期、归档、删除、质量校验、血缘、冷热分层和成本预算；
10. **容量验证**：每阶段记录实测连接数、tick/s、告警/s、P99、CPU/内存、网络和恢复时间，区分实测值、设计目标和外推值。

## 5. 项目框架与实施顺序

仓库采用 monorepo：`services/` 放 Go/Java 服务，`flink/` 放流作业，`apps/` 放双端，`packages/` 放共享协议客户端，`proto/` 放公共消息，`deploy/` 放 Compose/K8s，`observability/` 放观测配置，`docs/` 放设计和运维文档。目录和命名以 `08-工程实施与仓库规范.md` 为唯一细则。

实施顺序固定为：

```text
M1 核心闭环与契约
 -> M2 可靠性与可观测
 -> M3 K8s 化与小规模 HA
 -> M4 压测、混沌和容量调优
 -> M5 AI/补数/多市场等非主链路扩展
```

每个服务交付必须同时具备：接口契约、配置模板、健康检查、指标、结构化日志、幂等/重试策略、单测或集成测试、部署清单和 Runbook。公共消息、数据库表、Topic、部署拓扑或安全边界变更必须同步 ADR。

### 5.1 当前实施排期（2026-09 分支队列）

## 6. 最终冻结口径

- Kafka 是唯一实时事件总线，RabbitMQ 不与其并行承载同类事件；
- ClickHouse 存明细，Doris 做分析，MySQL 做事务，Redis 做热状态；
- U0~U1 可以单实例/混部，U2 起小规模 HA，U3 起正式分布式压测，U4~U5 才进入多 AZ 和百万连接专项；
- MySQL U0~U3 不默认分库分表；
- Tempo 与 SkyWalking 二选一，默认 OTel + Tempo；Profiles 单独使用 pprof/Pyroscope；
- Flink 不直接写 Redis/ClickHouse，行情快照由 quote-push 负责，明细由 ingest-worker 负责；
- 任何“完整生产拓扑”组件都必须有明确职责、启用阶段、故障恢复方式和验收指标，否则不纳入部署。

## 7. 运行时版本最终基线

版本不再使用无边界的 `24.x`、`7.x` 等表达。最终实施时固定 major.minor，允许在同一 minor 线内自动升级安全 patch；大版本升级必须新增 ADR，并完成兼容性矩阵、契约测试、基准压测、checkpoint/savepoint 恢复和滚动回滚验证。

| 类别 | 最终基线 | 不作为首发基线的候选 | 收敛理由 |
|---|---|---|---|
| Go 服务 | **1.25.x** | 1.26+ | 当前本机已具备 1.25.12；升级收益明确，兼容性风险可控 |
| Java/Flink | **构建/业务 JDK 21 LTS + Flink 1.20.x**；flink 模块编译目标 17（ADR-031，构建 JDK 可 21） | Flink 2.x | Java 21 生命周期更适合新项目；Flink 1.20 保留成熟状态和 Connector 路径；flink target 17 与本地验证环境对齐且无 21 专属依赖 |
| 消息总线 | **Kafka 4.1.x** | Kafka 5.x | KRaft、分区和重放模型延续；先验证 Strimzi 和 Flink Connector |
| 时序明细 | **ClickHouse 26.3.x LTS** | 更高非 LTS 线 | 选择 LTS 线，降低 SQL、Operator 和升级频率风险 |
| 分析查询 | **Doris 3.x LTS** | Doris 4.1.x、StarRocks | 2.1 已偏旧；3.x 作为保守升级线。dev compose 暂用 2.1.7 all-in-one 镜像且默认关闭（U0/U1 口径），U2 启用 Doris 时按本基线切 3.x |
| 缓存 | **Redis 7.4.x** | Redis 8.x | 满足 Cluster、租约、Lua、限流和 TTL；避免无收益的大版本迁移 |
| 前端 | **React 19.x + Node 24.x LTS** | React 20+ | 采用新稳定 React 线，但保留 AntD/klinecharts 兼容验证门 |

### 7.1 版本兼容门禁

1. Flink 版本必须与 Kafka Connector、Flink Kubernetes Operator、RocksDB 状态后端和 TA-Lib JNI 一起验证；
2. Kafka 版本必须验证 Strimzi、Schema Registry、ACL、生产幂等和消费者 offset 迁移；
3. ClickHouse/Doris 必须验证外表、ReplacingMergeTree、物化视图、Join、批量导入和归档；
4. Redis 必须验证 Cluster slot 迁移、gateway_slot fencing、Lua 脚本和客户端拓扑刷新；
5. React 19 必须验证 AntD、AntD Mobile、klinecharts、WebSocket SDK、PWA 和浏览器兼容性；
6. 本机和 CI 必须统一 JDK 21、Go 1.25、Node 24，禁止本机使用 Java 8 运行构建或压测。

### 7.2 版本升级顺序

```text
先升级构建运行时（Go/Java/Node）
 -> 再升级无状态服务
 -> 再升级 Kafka 客户端与 Schema
 -> 再升级 Flink 并验证 savepoint
 -> 再升级 Redis/ClickHouse/Doris
 -> 最后执行全量基准、混沌和恢复验收
```
