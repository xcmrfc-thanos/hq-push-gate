## 2. 组件职责表

| 组件 | 技术栈 | 职责 | 扩展方式 |
|---|---|---|---|
| hq-gateway | Go | 对接行情源 WS/模拟源；多源容灾切换；协议解析、基础清洗、Protobuf 标准化；输出 tick_raw | 按市场/数据源水平加实例 |
| Kafka | 3 broker | 流总线：削峰、解耦、重放 | 加 broker/分区 |
| Flink Job | Java | K线窗口、指标计算、规则匹配（KeyedState by market+symbol）、防抖、alert_event 输出 | 加 TaskManager |
| ingest-worker | Go 1.25.x（ADR-017 冻结） | 独立消费 tick_raw/snapshot 写 CK；失败不提交 offset 自动重放（U0 无独立死信 Topic，at-least-once）；与 Flink 完全解耦 | 加实例 |
| quote-push | Go | 消费 tick_raw，内存维护最新价，合并窗口默认 200ms（`QUOTE_PUSH_MERGE_WINDOW` 可调，见 ADR-009 注记）刷 Redis + 扇出 ws_push topic | 加实例（symbol 分片） |
| ws-gateway | Go | 维护海量 WSS 长连接（单实例按 20w 规划）；订阅管理；分级推送；心跳/背压 | 加实例（百万连接目标为 6 工作实例+2 冗余实例），客户端重连再平衡 |
| notify | Go | 消费 alert_event；**内嵌 alert-inbox 投递状态机**（PENDING/SENT/ACKED/EXPIRED，批量幂等落库）；展开用户投递并路由到 ws-gateway；邮件等适配器；重试/死信 | 加实例 |
| 业务服务 | SpringBoot3 | 用户/规则/分组/告警 inbox/查询编排；写 MySQL + Outbox | 加 pod |
| outbox-publisher | Go | 消费 outbox_event → Kafka（rule_bcast 等，ADR-026，§3.2 注记补入） | 低频发布，单实例即可 |
| APISIX | ×2 | 唯一公网入口：JWT、限流、路由、WSS 透传 | 加节点 |
| 存储 | CK/Doris/MySQL/Redis | 见 §6 存储设计 | 见 ADR-002 |

## 3. 核心数据流

### 3.1 实时行情与预警主链路（P0）

```
行情源/模拟源 ──▶ hq-gateway(解析/清洗/标准化, 5ms)
  ──▶ Kafka tick_raw (10ms)
  ├─▶ Flink: K线聚合/指标/规则匹配 (50~300ms)
  │     ├─ 命中(过冷却检查) ──▶ Kafka alert_event (10ms)
  │     └─ K线闭合 ──▶ Kafka snapshot_kline ──▶ quote-push 扇出 ──▶ ws_push（Kline payload，B21）
  ├─▶ quote-push: 最新价内存聚合, 合并窗口默认 200ms（可调）
  │     ├─ 刷 Redis 热快照
  │     └─ 扇出固定 ws_push（gateway_slot 路由） ──▶ ws-gateway ──▶ 客户端
  └─▶ ingest-worker ──▶ ClickHouse (异步, 可滞后)
alert_event ──▶ notify: alert-inbox 幂等落库(PENDING) ──▶ 推送 ws_push ──▶ 客户端 ACK
             └─▶ 落库/推送失败 ──▶ notify_retry ──▶ 死信(监控)
```

延迟预算（P99）：解析 5ms + Kafka 2×10ms + Flink 300ms + alert-inbox/notify 30ms + ws_push 10ms + 下行 10ms ≈ **< 400ms**（价格类规则），全链路目标 < 2s 留足余量。

### 3.2 规则热更新

```
用户提交规则 ──▶ APISIX ──▶ rule-service
  ├─ MySQL 持久化 (规则状态=生效) + outbox_event（同一事务）
  └─ outbox-publisher 发 Kafka rule_bcast (携带 market+symbol+ruleId+version)
Flink broadcast stream 消费 ──▶ 更新对应 KeyedState ──▶ 立即生效(秒级)
Debezium 消费 binlog ──▶ 对账任务周期校验 Flink 实际规则版本 ──▶ 差异自动重发 bcast
```

### 3.3 查询链路（读写分离 + 多级缓存）

```
K线/行情查询 ──▶ quote-service
  1. 本地 Caffeine(最热标的, 1s) ──命中──▶ 返回 (P99<5ms)
  2. Redis 快照 {market}:{symbol} ──命中──▶ 返回 (P99<10ms)
  3. Doris(外表映射CK, 分区裁剪) ──▶ 返回并回写缓存 (P99<500ms)
历史告警 ──▶ MySQL 分页(简要) / Doris(分析)
```

> 实现现状（审计注记）：第 1 级本地 Caffeine 缓存**未实现**，现行为 Redis 快照 → CK 直查
> （`/quote/kline` 经 KlineService，全参数绑定）；Doris 外表随 U2 启用 Doris 后接入。
> 本图为目标态拓扑，P99 口径届时按第 1/2 级复评。

### 3.4 AI 筛选链路（可选，M3）

```
自然语言 ──▶ ai-query: LLM 转结构化条件(JSON Schema 校验, 防幻觉)
  ──▶ 条件编译为 Doris SQL(白名单函数/字段) ──▶ Doris 执行筛选
  ──▶ 结果列表 ──▶ LLM 润色回答 / 保存为分组 / 生成预警规则
高频条件命中 Redis 缓存, 免 LLM 调用
```

## 4. 高可用（HA）设计

### 4.1 组件级 HA 策略

| 组件 | HA 机制 | 故障切换时间 |
|---|---|---|
| APISIX | 多节点 + LB/DNS；无状态 | 秒级 |
| 业务服务/notify/quote-push | K8s 多副本 + PDB + 反亲和 + 探针自愈 | < 30s |
| hq-gateway | 多实例按**数据源分片**（每实例独占 source/分区集，天然不重不漏——现行方式）；"分区 leader 选举主备热备"为目标态未实现（登记 docs/12 §2.6） | < 10s |
| ws-gateway | 多实例；实例故障客户端自动重连其他实例（LB 分流），重连后 REST 补拉 | 1~3s（客户端侧） |
| Kafka | RF=3，min.insync.replicas=2，acks=all | broker 切换 < 10s |
| Flink | HA（K8s JobManager 高可用）+ 增量 checkpoint 30s + RocksDB | TM 故障自动恢复 < 2min；JM 故障 < 1min |
| MySQL | 一主一从半同步 + Orchestrator 故障切换 | < 60s |
| Redis Cluster | 3主3从，分片自愈 | < 10s |
| ClickHouse | ReplicatedMergeTree 双副本 | 自动同步 |
| Doris | 多 FE + BE 多副本 | 自动 |

### 4.2 故障场景矩阵（混沌演练清单）

| 注入故障 | 影响 | 系统行为 | 验证目标 |
|---|---|---|---|
| kill Kafka 单 broker | tick 部分区不可写 | 生产者重试 + 分区 leader 重选举 | 不丢数，恢复 < 30s |
| kill Flink TM | 预警计算中断 | checkpoint 恢复重启，规则状态还原 | 告警不丢（at-least-once），MTTR < 2min |
| kill MySQL 主 | 规则写入失败 | Orchestrator 提升从库；服务连接池重连 | 规则变更延迟 < 1min |
| kill ws-gateway 实例（≈15w 连接） | 大规模重连 | 其余实例恒速准入（5w/s）+ 客户端抖动退避 + TLS 复用；Redis 路由更新 | 保留窗口内投递可补拉，重连风暴不打崩集群 |
| ws-gateway 全组滚动发布 | 分批断连 | maxUnavailable: 0 + drain 通知逐实例摘除；HPA 先扩后缩 | 用户无感（应用层自动重连） |
| kill ClickHouse 节点 | 历史查询部分失败 | 副本接管；ingest-worker 写入重试 | 查询可用，写入不丢 |
| 行情源断流 | 无新 tick | hq-gateway 切备用源/模拟源；断流告警 | 切换 < 10s |
| Doris 过载 | AI 筛选慢 | 熔断 + 排队限流；不影响预警链路 | 链路隔离验证 |

### 4.3 降级与熔断策略

1. **链路优先级**：实时预警 > 行情推送 > 查询 > AI 筛选 > 统计分析；
2. 行情推送可降级：拉大合并窗口 500ms→2s、只推自选标的；**预警推送不可降级**；
3. 查询降级：Doris 慢时只读 Redis/本地缓存返回旧快照（附 stale 标记）；
4. AI 服务熔断（Sentinel/Resilience4j），熔断期间返回缓存结果；
5. 推送洪峰：ws_push topic 堆积超过水位 → 丢弃旧行情快照只推最新（快照类可丢）；alert 类不可丢，走重试。

### 4.4 数据可靠性

1. tick 链路 at-least-once：Kafka acks=all；ingest-worker 写 CK 失败重投，CK 唯一键去重（ReplacedMergeTree）；
2. 告警链路 at-least-once + 端到端幂等：alert_event 使用 event_id，面向用户投递使用 delivery_id；alert-inbox、notify、ws-gateway、客户端按 delivery_id 去重；
3. 规则变更：MySQL 为 source of truth，Kafka bcast 若丢失由 Debezium 对账补偿（周期 1min），保证最终一致；
4. Kafka 保留 3 天可重放；CK 冷数据归档 S3。

## 5. 高性能（HP）设计

| 手段 | 位置 | 说明 |
|---|---|---|
| Protobuf 序列化 | 全内部链路 | tick 消息 ~40B，比 JSON 小 60%+，解析 CPU 低 |
| 批量 + 合并 | hq-gateway 攒批发 Kafka；quote-push 合并窗口默认 200ms（可调）；ws-gateway 批量帧下发 | 摊薄网络/序列化开销 |
| 多级缓存 | Redis → CK（Doris U2+ 接入；本地 Caffeine 为规划态） | 热点行情经 Redis 快照返回 |
| 预聚合 | CK 物化视图：1m→5m→日线增量聚合 | 大周期查询不扫明细 |
| 分区裁剪 | CK/Doris 按 (market, toYYYYMM(timestamp)) 分区 | 历史查询只扫命中分区 |
| Flink 优化 | RocksDB 增量 checkpoint；事件时间与 watermark；并行度=分区数；规则索引按 symbol 预过滤；外部写入由独立消费者承担 | 吞吐 ≥ 10w tick/s 冗余 |
| 连接层 | Go goroutine + gorilla/websocket（epoll 由 net poller 承担；"标准库深度调优/gnet"为目标态）；每连接读写缓冲 4KB 上限 | 单实例按 20w 连接规划（能力上限 30w~50w，见 §6.2-A） |
| 背压丢弃 | ws-gateway 按连接 QuoteBuffer 丢旧保新（每 symbol 仅留最新）+ KlineCh(4)/AlertCh(256) 有界队列 | 行情可丢旧，预警不丢 |
| 异步化 | notify 全异步 IO；REST 查询无阻塞调用（WebFlux/虚拟线程可选） | 尾延迟可控 |

## 6. 高并发（HC）设计

### 6.1 并发模型分层

```
接入并发:  APISIX 限流(IP/用户级令牌桶) → 业务服务无状态水平扩(HPA)
连接并发:  ws-gateway 集群承接长连接, 客户端↔实例映射存 Redis, 扩容靠重连再平衡
计算并发:  Kafka 分区数(24) = Flink source 并行度; keyBy(market+symbol) 保证局部有序
推送并发:  每 symbol 的扇出在 quote-push 分片处理; 固定 ws_push 通过 gateway_slot 路由
数据并发:  CK 分布式表分片写; Doris FE 负载均衡读; MySQL 读写分离
```

### 6.2 WebSocket 推送链路（百万连接设计，核心）

#### A. 连接层选型对比（谁都能扛，选生态和团队栈）

| 技术栈 | 单机能力 | 评价 | 结论 |
|---|---|---|---|
| **Go（标准库 net + netpoller）** | 30w~50w/节点（goroutine/conn，~10KB 栈） | 生态好、开发快、GC 在大连接数下需调优（GOGC/GOMEMLIMIT）；可换 gnet（event-loop）压内存 | **采纳（默认）** |
| Java Netty | 50w~100w+/节点（epoll + pooled ByteBuf + ZGC） | C1M 实战案例最多（Twitter/推送厂商）；JVM 调优门槛高，与 Go 服务双栈 | 采纳（备选，单机密度优先时切） |
| smart-socket | 尚可 | 国产轻量 AIO，社区/生产案例远少于 Netty/Go，论文引用弱 | 否决 |
| C/Envoy 定制 | 最高 | 开发成本不成比例 | 否决 |

> 关键认知：**百万连接不是语言问题，是内核参数 + 内存预算 + 集群架构问题**。Go/Netty 都能在单机压到 50w+，集群化后语言差异被稀释；选型看团队栈（本团队 Go/Java 双栈，选 Go）。

#### B. 单机 C1M 内核与内存预算（每 ws-gateway 节点）

```
内核参数（节点级 tuning，进部署基线）:
  fs.file-max / nofile          ≥ 1,048,576（ulimit -n）
  net.core.somaxconn            = 65535
  net.ipv4.tcp_max_syn_backlog  = 65535
  net.core.rmem_max/wmem_max    = 16MB
  net.ipv4.tcp_rmem/wmem        = 4096 87380 16777216（自动缓冲，空闲连接仅占几KB）
  net.ipv4.tcp_mem              按页调整为机器内存 ~5%
  net.ipv4.tcp_keepalive_time   = 600
  TCP_DEFER_ACCEPT + TCP_NODELAY
```

| 每连接内存项 | 预算 |
|---|---|
| 内核 socket（idle 自动缓冲收缩后） | ~8KB |
| 用户态读/写缓冲（上限 4KB，池化） | ~8KB |
| goroutine 栈 + 连接状态（userId/订阅表/限速器） | ~12KB |
| **合计/连接** | **~28KB** |
| **单节点 20w 连接** | **~5.6GB + 常规开销 → 16GB 节点作为连接层基线** |

**集群规模**：100w 连接按 20w/工作实例规划，部署 **6 个工作实例 + 2 个故障冗余实例**（双可用区打散）；扩容不改变协议和 Topic。

#### C. 分级推送策略（百万连接下扇出削峰的关键）

连接分三级（客户端声明 + 服务端按页面可见性动态调整）：

> 实现现状（审计注记）：本表"页面可见性分级"为规划态**未实现**；现行按**套餐权益差频**
> （B22/ADR-040/ADR-041：free 10s / vip 3s，docs/10 §3.4），分级维度从"客户端可见性"
> 演进为"套餐档位"，扇出削峰目标不变。下表保留为 U3+ 可见性分级的扩展设计。

| 级别 | 行情推送 | 告警推送 | 占比假设（1M 在线） |
|---|---|---|---|
| QUOTE_FULL（前台盯着行情） | 500ms 合并帧 | 实时 | 10%（10w） |
| QUOTE_SLOW（后台/App 切走） | 2s 合并帧，仅自选前 20 | 实时 | 30%（30w） |
| ALERT_ONLY（退订行情） | 无 | 实时 | 60%（60w） |

扇出数学（最坏情形：全部 5000 活跃标的同时跳价）：

```
每实例扇出 = Σ(本级连接 × 本级帧率 × 帧大小)
  = 20w×(10%FULL: 2fps×2.5KB + 30%SLOW: 0.5fps×1KB)   # 20w/工作实例（6 工作+2 冗余，100w÷6）
  ≈ 20w × 0.65KB/s ≈ 130MB/s ≈ 1.04Gbps/实例
集群 egress(6 工作实例) ≈ 6.2Gbps → 万兆网络可承载
对比不做分级：1M×2fps×2.5KB = 40Gbps（不可行）→ 分级是必要条件
```

#### D. 订阅与路由（原设计保留，规模验证）

```
[订阅] 客户端 ──subscribe(symbols)──▶ ws-gateway
        └─ 本地 connTable 注册; Redis: sub:{userId}, conn:{userId}→gatewayId (TTL心跳×3)
[扇出] quote-push: 消费 tick_raw → 合并窗口默认 200ms（可调）→ 查 gwsubs:{gatewayId}(订阅聚合)
        → 按 gateway_slot 路由写固定 ws_push（只投给需要该 symbol 的实例）
[推送] ws-gateway 手动消费自己持有的固定分区 → 本地 connTable 反向索引过滤 → 批量合并帧下发
        ├─ 单连接限速 ≤20 帧/s; QuoteBuffer 丢旧保新（每 symbol 仅留最新一条）
        └─ alert 走独立高优队列，绝不丢弃
```

Redis 容量验证：1M `sub:{userId}` + 1M `conn:{userId}` + 8 个聚合 Set ≈ 数 GB，3主3从分片后轻松。notify 告警路由按 conn:{userId} 批量 MGET，告警速率（~1k 事件/s）远低于该读压力。

#### E. 重连风暴防护（百万连接 HA 的头号敌人）

1. 客户端：指数退避 1s→60s **+ 全连接 0~5s 随机抖动**（打散 1M 重连波）；
2. TLS 握手成本：1M 重连 × ECDHE ≈ 1ms CPU/次 → 集群需 ~16 核分钟；**启用 TLS session ticket 复用**（重连握手降 ~80% CPU）；
3. 服务端：连接接入采用**恒速准入**（token bucket，如 5w 新连接/s/集群），超出排队重试；
4. LB：慢启动（slow-start）+ 连接耗尽（conn drain）梯度切流；新实例 readiness 门控后才接收；
5. 认证复用：重连使用短期 ticket（握手时免完整 JWT 校验，防认证层被打爆）。

#### F. 扩缩容

新 ws-gateway 实例 → 注册 gateway_id 并租约固定 `ws_push` 槽位、手动消费对应分区；客户端重连由 LB 分流 → Redis 路由更新。缩容由 **SIGTERM 触发 hub.DrainAll 下发 `sys.drain`**（K8s preStop 仅宽限等待，deploy/k8s/README §实现口径）→ 客户端主动重连 → 释放槽位 → 优雅退出（60s 宽限）。HPA 指标：**连接数 + CPU 70%**（"内存双驱动"为规划态），不创建动态 Topic。

> 内存预算 vs 清单：本节 ~28KB/连接为 20w 连接/16GB 节点的**扩容目标预算**；dev K8s 清单
> ws-gateway limit 已按 B24 调至 2Gi（U0 规模），连接层扩容时按本预算上调节点规格。

### 6.3 限流体系（三级）

| 层级 | 机制 | 参数 |
|---|---|---|
| 网关 | APISIX limit-count（IP 维度防滥用基线） | **120 req/60s/IP**（≈2/s，现行配置）；per-user/API 维度配额为 U2+ 演进项 |
| 服务 | 进程内并发帽 + 熔断（ai-query LLM 网关 max_concurrency/日配额；notify 渠道 CircuitBreaker）；Sentinel 未引入（规划态） | AI 类并发 10、全局日配额 2000；渠道全局/单用户日额度可配 |
| 连接 | ws-gateway 单连接消息速率 + 订阅数上限 | ≤ 20 帧/s，≤ 200 symbol/连接 |

### 6.4 洪峰削峰

1. 开盘/急跌场景告警爆发：alert_event 流量脉冲 → notify 消费速率恒定，多余堆积在 Kafka（天然缓冲）；
2. 推送侧按用户配额整形，防止瞬时打满 ws-gateway；
3. 压测场景：模拟源可注入「开盘脉冲」（10 倍速率持续 30s）验证削峰。

## 7. 存储设计与中间件规模匹配

### 7.1 各中间件在链路中的位置（谁在热路径，谁不在）

| 中间件 | 是否热路径 | 规模压力 | 结论 |
|---|---|---|---|
| **Redis Cluster** | ✅ 是（连接路由/订阅/快照） | 1M conn/sub 键 + gwsubs 聚合，数 GB | **百万连接的核心依赖**，3主3从起步，扩分片；客户端心跳 TTL 容忍单分片故障 |
| Kafka | ✅ 是（tick/扇出） | 10w msg/s，6MB/s | 压力极低，瓶颈不在 MQ |
| **MySQL** | ⚠️ 仅告警链路（alert-inbox 落库） | 写速率=告警事件速率（≤~1k/s，受 notify 消费速率整形，批量写）；其余为规则 CRUD/用户/记录分页读 | 在告警路径上但写入有界且可重试（落库失败走 notify_retry 不丢）；主从 + 读写分离足够，无需替换 |
| **Doris** | ❌ 否（查询/筛选离线侧） | 1w QPS 查询（缓存后），与连接数无关 | 挂了只影响历史查询/AI 筛选，预警推送不受影响（故障域隔离） |
| ClickHouse | ❌ 否（入库异步） | 10w 行/s 写入 | ingest 攒批，可滞后可重放 |
| APISIX | ✅ 是（REST/WSS 入口） | 公网 TLS 终止、边缘 JWT/限流和 Upgrade 代理 | ws-gateway 复核 WS token 并做业务授权 |

> 澄清常见疑问："百万连接是否要换掉 MySQL/Doris？"——**连接层瓶颈只在 ws-gateway + Redis + 出口带宽**；MySQL 仅在告警投递路径（写入速率=事件速率，有界且可重试），Doris 不在任何推送热路径上，规模匹配无需变更。

### 7.2 存储分工

| 存储 | 数据 | 关键设计 |
|---|---|---|
| ClickHouse | tick 明细、K线（全周期） | Distributed + ReplicatedMergeTree；分区 (market, 月)；排序 (symbol, timestamp)；TTL 热数据 1 年；更冷归档 S3；物化视图预聚合大周期 |
| Doris | 告警事件明细、指标统计；外表映射 CK tick/kline | 多 FE + BE 三副本；统一查询入口（MySQL 协议）；AI 筛选执行引擎 |
| MySQL | 用户、规则、公式、分组、告警简要记录、市场/标的元数据 | 主从半同步；规则表按 user_id 索引；binlog→Debezium 对账 |
| Redis | 快照 `{market}:{symbol}`；订阅关系；连接映射；限流/冷却计数 | Cluster 3主3从起（百万连接场景按 §6.2-D 容量扩分片）；快照 TTL 1 天滚动 |

**边界**：MySQL 不存时序；Redis 不存历史；CK 不直接对前端；Doris 承载全部分析型查询。

## 8. 资源隔离（K8s namespace）

| namespace | 内容 | 保障 |
|---|---|---|
| ns-realtime | hq-gateway、Kafka、Flink、quote-push | 资源 requests=limits，最高优先级，禁止其它负载抢占 |
| ns-push | ws-gateway、notify | 独立资源池 |
| ns-query | 业务服务、APISIX、Doris 查询 | 与实时隔离 |
| ns-ai | ai-query（可选） | 低优先级，可整体熔断 |
| ns-offline | ingest-worker、补数、压测控制器 | BestEffort，可牺牲 |

## 9. 多市场扩展

1. 所有消息（Protobuf）、所有表、所有 Redis key 强制携带 `market` 字段；
2. 新增市场 = 新增 hq-gateway 实例 + 市场字典配置（时区、交易时段、最小变动单位），上层零改动；
3. Flink 窗口参数由广播流下发的市场元数据驱动，不硬编码 A 股交易时间；
4. 模拟源支持生成 `HK/US/CRYPTO` 假想数据用于 M4 扩展性实验。

## 10. 安全设计

1. 公网仅暴露 APISIX（443）；Kafka/CK/Doris/MySQL/Redis/Flink UI 全部内网；
2. 传输：公网 TLS 在 APISIX 终止，APISIX 到 ws-gateway 使用受控 Upgrade 代理和内网 TLS；
3. 认证：APISIX 做边缘 JWT 校验，ws-gateway 在 Upgrade 阶段复核短期 access token 或一次性 reconnect ticket，并执行市场/标的授权；单用户并发连接数上限（默认 5 为规划态，现行 APISIX limit-conn 10/IP + ws-gateway 侧无按用户连接帽）；
4. 授权：订阅 ACL——用户只能订阅白名单市场/标的；管理 API 走 RBAC + 独立域名；
5. 限流三级（§6.3）+ 租户级预留：网关（limit-count）、连接（订阅数 ≤200、帧率 ≤20fps）、业务（进程内并发帽/日配额）；租户级预留为 U3+ 多租户演进项；
6. 公式沙箱（M3）：表达式白名单函数 + 资源限制（CPU/时长）+ 禁止系统调用；
7. 推送内容安全：告警内容服务端渲染，客户端不解释执行；API 响应统一 `code/msg/data` 防 JSON 劫持；
8. 依赖安全：镜像扫描（trivy）、依赖审计 CI 门禁、secrets 用 K8s Secret + 外部密管（不进 git）；
9. 审计：规则变更、登录、管理操作全量入 Loki（不可抵赖排查）；
10. DDoS 预案：云 LB 层 IP 限速 + APISIX 黑白名单；恒速准入天然吸收连接型攻击（slowloris 由握手超时 + 准入队列防御）。
