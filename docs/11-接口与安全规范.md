## 1. 接口面与版本控制

### 1.1 接口面划分（五类，口径唯一）

| 接口面 | 前缀 | 暴露范围 | 鉴权 | 版本策略 |
|---|---|---|---|---|
| 公网用户面 | `/api/v1/*` | APISIX → 公网 | 边缘 JWT + 服务内复核（双层） | path 版本 `/api/v1`，破坏性变更升 `/api/v2` 并行一个过渡期 |
| 公网开放面 | `/open/v1/*` | APISIX → 公网（Branch 18 起） | AK/SK 签名（§5） | 同上 |
| 内部面 | `/internal/*` | 不出公网（APISIX 黑洞路由） | X-Internal-Token | **不带版本**：内部面随 monorepo 同版本发布，无兼容承诺 |
| 源接入面 | `/ingest/*` | 不出公网 | 网络位置 + 白名单 | 同内部面 |
| 健康面 | `/healthz` `/readyz` `/metrics` `/actuator/*` | 内网管理端口 | 无（网络隔离） | 永不版本化 |

【现状】`/api/v1` 单档已全量执行（Java 全部 Controller、ai-query、APISIX 路由）；`/healthz` 等健康面无版本——均符合本节，成文固化即可。
【现状】ai-query 公网别名：APISIX `POST /ai/query` → rewrite `/api/v1/ai/query`。**规则：短别名只是边缘路由产物，契约文档只登记 `/api/v1` 规范路径。**
【修复·Branch 17】无。

### 1.2 版本升级规则

- **不算破坏性变更**（/v1 内直接做）：新增可选请求字段、新增响应字段、新增端点、新增错误码。
- **算破坏性变更**（必须 /v2）：删除/改名已有字段、改字段类型或语义、改错误码含义、改鉴权方式。
- WS 帧协议（docs/04 §7）在 `sys` 帧预留 `{"code":"version","data":{"v":1}}` 协商标记，U3 前不启用。

## 2. 报文信封

### 2.1 REST 信封（全局唯一格式）

```json
{ "code": 0, "msg": "ok", "data": { } }
```

- 成功：`code=0`，`data` **必须存在**（无内容时为 `{}` 或 `[]`，禁止 null）。
- 失败：`code≠0`，`data` 省略；`msg` 为可直接展示的中文短句；`HTTP status` 按 §3 分段映射，禁止"业务错误恒 200"。
- 分页：游标式 `?cursor=&limit=`（默认 50，上限 200），响应 `data = {"items":[...], "next_cursor":"..."}`，`next_cursor` 为空串表示到底。不用 offset/页码。

### 2.2 实现载体

| 栈 | 载体 | 现状→修复 |
|---|---|---|
| Java | `ApiResult.ok(data)` / `ApiResult.err(code,msg)` | ✅ 已做（U1 收尾：10 文件手写 Map.of 全量替换；OpenApi 1 处随 D11-3 收口） |
| Go | `packages/httpx`：`WriteJSON` / `Err(w, status, code, msg)` | ✅ 已做（U1 收尾：httpx 共享包，37 调用点统一） |
| Python | 保持 routes 内联 dict；FastAPI 校验错误挂全局 exception_handler 转信封 | 【登记 U2，docs/12 §2.6】 |

### 2.3 WS 帧信封（另一套，不混用）

- 服务端→客户端 `{type, data}`；客户端→服务端 `{type, ...}`（docs/04 §7 冻结）。
- 【登记 U2，docs/12 §2.6】新增错误帧 `{type:"error", data:{code,msg}}` 替换静默丢弃（ws_server.go 非法帧 continue）；`sys.code` 字符串枚举与 REST 数值 code 明确为两个命名空间（文档口径，不改代码）。

### 3.2 降级标记

`503xx` 且涉及"读到旧数据"的场景，`data` 中附 `"stale": true`（docs/04:250 冻结口径，目前无场景触发；快照兜底缓存启用时接入）。

### 3.3 429 必带 Retry-After（2026-09-10 契约登记，缺陷 #24 收口）

所有 `429xx` 响应必须携带 `Retry-After` 头（秒数，整数字符串）：

| code | Retry-After | 依据 |
|---|---|---|
| 42901（/open/v1 per-AK） | `60` | 限流窗口为 60s 滑窗（OpenApiVerifier） |
| 42901（ai-query） | 距 CST 午夜秒数；上游 429 冷却场景 `60` | 与 `llm:quota:*:{date}` 配额键过期时刻一致 |
| 42910（套餐配额） | `3600` | 配额为非周期重置硬上限，给保守小时级退避 |

## 5. 开放面安全协议（AK/SK + Timestamp + Nonce + Sign）

> Branch 18 实装。设计目标：防篡改、防重放、防密钥入 URL/日志。兼容现有 docs/10 §6.1 的 api_developer_config 表（access_key/app_secret），**不再用裸 `Bearer accessKey`**（该写法仅允许在内网调试，公网禁用）。

### 5.1 REST 签名协议

请求头：

```
X-Access-Key:  <access_key>
X-Timestamp:   <毫秒时间戳>
X-Nonce:       <UUID v4，一次一换>
X-Signature:   <hex>
```

签名串（\n 连接）：

```
StringToSign = METHOD \n PATH \n CANONICAL_QUERY \n X-Timestamp \n X-Nonce \n SHA256_HEX(BODY)
X-Signature  = HEX( HMAC-SHA256( app_secret, StringToSign ) )
```

- `CANONICAL_QUERY`：query 参数按参数名字典序、值 RFC3986 urlencode 后 `k=v&k=v` 拼接；无参数为空串。
- 空 body 取 `SHA256("")`。

服务端校验顺序（biz-service open filter，Redis 缓存 developer 配置 60s）：

1. `X-Access-Key` 查 `api_developer_config`，不存在/禁用 → 40104；
2. `|server_now - X-Timestamp| ≤ 300s` → 否则 40105（服务器间时钟偏差按 NTP ±60s 保障）；
3. nonce 防重放：`SET open:nonce:{ak}:{nonce} 1 NX EX 300`，失败 → 40106；
4. 常时比较签名（`hmac.Equal`），不符 → 40104。

**Redis 依赖故障口径（fail-close，2026-09-11 补）**：nonce 防重放与配置缓存依赖 Redis；
Redis 不可用时开放面一律 **fail-close**（返回 50300，不放行）——防重放窗口是安全边界，
fail-open 等于关闭防重放。渠道凭据热加载（§7.2，notify 侧）同理：缓存过期且回源失败时
沿用最后已知配置继续投递（可用性优先，凭据非增量安全边界），两类依赖口径不同、各自成文。

### 5.2 开发者 WS 接入（ticket 模式）

禁止 `?accessKey=` 直连（AK 会进访问日志）。改为：

1. 开发者先用 §5.1 签名调用 `POST /open/v1/ws-ticket` → 返回 60s 一次性 ticket（Redis，`open:ws:{ticket}` → user_id）；
2. `wss://…/ws?ticket=xxx`，ws-gateway Authenticator 加 ticket 分支换 uid 后立即删除。

### 5.3 出站 Webhook 防重放补齐

现格式 `X-Hook-Sign: sha256=HEX(HMAC(body))` 可被无限重放。Branch 18 升级为：

```
X-Hook-Sign:  sha256=HEX( HMAC-SHA256( app_secret, ts + "." + nonce + "." + SHA256_HEX(body) ) )
X-Hook-Timestamp / X-Hook-Nonce 头同步携带
```

接收方校验时间窗 ±300s + nonce 去重；旧格式保留一个过渡版本（`X-Hook-Version: 1|2`）。重试沿用 2s/5s/10s，nonce 每次重试重新生成。

## 6. 服务商回调安全（入站）

- `POST /internal/hooks/dmail|sms`：APISIX 单独路由 + IP 白名单 + `X-Hook-Sign`（HEX(HMAC-SHA256(HOOK_SECRET, body))）恒时比较。
- 重放威胁模型成文：退订/回执类事件按 `(event_id, user)` 幂等落库，重放无副作用，不引入 nonce（服务商 EventBridge 不支持回传自定义 nonce）。

## 7. 凭据与密钥管理

### 7.1 JWT claim 契约（三方对齐——现状断裂，Branch 17 修复）

统一 claim：`sub`=uid 字符串（保留）、`uid`=数值（ws-gateway 用）、`typ`=access|refresh（三端都验）、`key`=APISIX consumer key（`hq.jwt.consumer-key` 配置，默认 hqweb-key）。

- 签发：`TokenService` 增补 `uid`/`key` claim；
- ws-gateway：验 `typ=access`（golang-jwt 默认验 exp 保留）+ `uid>0`；
- APISIX：jwt-auth 现有 consumer 配置不动，靠 `key` claim 对齐。
- 【现状审计】现网三处不一致：TokenService 无 uid/key claim → ws-gateway 拒真实用户（"missing uid"）→ APISIX 拒无 key claim 的 token；**当前端到端只有 bench 自签 token 能走通**。
- 【bench 例外（Step1 D07-1 口径修正）】ws-bench 直连 ws-gateway 不经 APISIX，自签 token 仅需 `uid/typ`（`sub/key` 非必需）。
- **token 吊销语义（ADR-040，2026-09-07 成文）**：U1 接受 access 2h 不可吊销（无黑名单）；ws-gateway 每 5min 按 user_id 复核 user_vip 配额/状态（Redis 缓存 user_vip，变更即失效），降级/封号后存量 WS 连接在下一复核周期被摘除——兜底"套餐降级持旧配额"与"封号仍收告警"。

### 7.2 平台主密钥（渠道凭据密文化）

- `HQ_MASTER_KEYS="k1=<hex64>[,k0=<hex64>...]"`：主密钥表（KID 轮换，首个为当前加密钥，其余仅解密）；32 字节 hex（`openssl rand -hex 32`），env/K8s Secret 注入。`HQ_MASTER_KEY=<hex64>` 兼容为 `k1=` 单钥（legacy）。三端实现同格式：Go `packages/secretx` / Java `SecretBox` / Python `secrets.py`。
- 密文格式（Go/Java/Python 三端实现一致，格式含 KID 支持轮换，ADR-035）：`v1:<kid>:` + base64( 12B nonce ‖ AES-256-GCM ciphertext ‖ 16B tag )。
- 适用：`llm_provider.api_key_enc`、`notify_channel.config_enc`（Branch 16 起）；`api_developer_config.app_secret` 加密化随 Branch 18。
- 口径：源码/测试/示例零凭据字面量；凭据只进 env 或 DB 密文；日志脱敏（`sk-***last4`）。
- **轮换 Runbook（2026-09-11 补，格式支持≠流程可执行）**：
  1. **上线新钥**：`HQ_MASTER_KEYS` 头部追加新 KID（如 `k2=<new>,k1=<old>`）——三端"首个为加密钥"语义即切换新写入；
  2. **灰度滚动**：按 notify → ai-query → biz-service 顺序重启，滚动期间新旧密文并存（旧密文 k1 可解，无窗口故障）；
  3. **存量重加密**：管理端批处理（读时用旧钥解密 → 新钥加密 → 回写），或懒式"读时透明重写"（读取命中非首个 KID 时解密后立即以新钥回写，带重写失败仅记日志不阻塞）；
  4. **移除旧钥**：扫描确认三表无 `<旧kid>:` 前缀密文残留后，从 `HQ_MASTER_KEYS` 移除旧项并重启；移除后旧密文不可解（不可逆，扫描前置为硬性步骤）。
